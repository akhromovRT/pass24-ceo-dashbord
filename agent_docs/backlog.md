#### P3.0.1 — Перформанс «1С-вида» по публичному интернету
- **Жалоба:** «Без VPN очень сильно тормозит данный интерфейс, иногда время ожидания достигает минуты».
- **Корень:** `/api/v1/debt-snapshots/latest` отдаёт целиком все ~6 тыс. строк snapshot'a + 297 actual_org_totals + workflow_by_org + diffs. На боевом файле это ~3–5 MB JSON, в проде без gzip и без HTTP/2 это даёт минуту ожидания на 4G/мобильном.
- **Fix (по эскалации эффорта):**
  - **(а)** Включить `gzip on` в `frontend/nginx.conf` для `application/json` (тип уже включён в стандартных profiles, проверить — возможно, не работает из-за `gzip_proxied off`). Ожидаемый выигрыш 5–10× по размеру.
  - **(б)** Включить HTTP/2 (если ещё не) — `listen 443 ssl http2;` в nginx-блоке.
  - **(в)** Server-side кеш `/debt-snapshots/latest` по `snapshot.id` (snapshot immutable между импортами): простой `lru_cache` на N минут или `Cache-Control: max-age=300` на ответ + `ETag = snapshot.id`. После применения миграции данные не меняются — кеш безопасен.
  - **(г)** На уровне ответа: не отдавать `rows` целиком, отдавать только buyer-уровень. Контракты/документы подгружать lazy при раскрытии узла TreeTable (отдельный GET `/debt-snapshots/{id}/rows?parent_row_id=...`).
- **Срок:** (а)+(б) — 30 минут (вероятно решат проблему). (в) — 1 час. (г) — 1 день (требует изменения фронта).
- **Зависимости:** нет.

#### P3.0.2 — Фильтр «Только активные клиенты» в «1С-виде»
- **Жалоба:** «Здесь все должники — и активные клиенты, и те, кто в дальнейшем пойдут на списание. Прошу добавить ещё один фильтр: если клиент активный, чтобы можно было отфильтровать по ним.»
- **Корень:** существующий `only_regular=true` отсекает только Транзит и Потенциальных, но оставляет CHURNED — это и есть «те, кто пойдут на списание». Софья хочет ещё более узкий срез — `Organization.status == ACTIVE` (опционально + SUSPENDED).
- **Fix:** заменить пару чекбоксов «Только наши клиенты» / «Только расхождения» на компактный фильтр-блок:
  - Селектор статусов клиента (SelectButton или MultiSelect): «Активные» / «+ Приостановленные» / «+ Отток (к списанию)» / «Все наши». По умолчанию — «Активные».
  - Чекбокс «Только расхождения» оставить как есть.
- Backend: добавить второй query-параметр к `/debt-snapshots/{id}`: `org_statuses: list[str] = ["active"]` (csv `active,suspended`). Логика фильтрации та же, что и для `only_regular`, только множество статусов параметризуемо. `only_regular=true` оставить для обратной совместимости как alias `org_statuses=active,suspended,churned`.
- Тесты: расширить `TestOnlyRegularFilter` ещё одним кейсом с `org_statuses=active`.
- **Срок:** 1–2 часа. **Зависимости:** нет.

#### P3.0.3 — Общий долг считается по всем юр.лицам, включая Транзит/Отток
- **Жалоба:** «Несмотря на то, что я проставила статусы по старым клиентам, общий долг формируется всё равно по всем юр.лицам (не только по активным).»
- **Корень:** `/billing/debtors` фильтрует только `excluded_from_analytics=False`, не отсекая Транзит и Отток. Их `Organization.total_debt` продолжает попадать в плитку «Общий долг» в шапке Должников и в плитку «Долг» на Dashboard. После того, как Софья переводит клиента в TRANSIT/CHURNED, она ожидает, что цифра «Общий долг» уменьшится — но этого не происходит, потому что начисления остановились, а накопленный `total_debt` остался.
- **Бизнес-вопрос (нужно решение CEO):** что показывать как «Общий долг»? Варианты:
  - **(А)** Только ACTIVE+SUSPENDED — самый агрессивный, ушедшие просто исчезают.
  - **(Б)** ACTIVE+SUSPENDED отдельно, CHURNED+TRANSIT отдельно («к взысканию / к списанию» — две метрики в шапке).
  - **(В)** Оставить как есть, но добавить лёгкий способ исключить группу из цифры (тогл в шапке).
- **Рекомендую (Б):** в `/billing/debtors` (или `/billing/segments`) вернуть три цифры — `total_debt_active`, `total_debt_writeoff` (CHURNED+TRANSIT), `total_debt`. В шапке `DebtorsView.vue` показать «Долг активных» как основной, «К списанию» — отдельной плиткой меньше. Дашборд — обновить плитку «Долг», показывать `total_debt_active` (с подсказкой «без оттока/транзита»).
- **Срок:** 2–3 часа (бэк + UI + обновить test_api_billing). **Зависимости:** согласование с CEO, какой вариант (А/Б/В) выбираем.

  - **Дата платежа в экспорте:** для отчётов уровня «платежи» (а не агрегаты) гарантировать колонку `doc_date`. В CSV/Excel-экспорте включать её первой после `Контрагент`.
- **Срок:** 1 день (3 эндпоинта × расширение параметров + UI + экспорт + тесты). **Зависимости:** уточнить у Софьи, какой именно отчёт она использует — «Реестр платежей» или «Поступления»; от этого зависит, какой `ReportTemplate.preset` правим в первую очередь.

## Качество и DX

### Применение шаблона composition в /reports теряет metric/period
- Сохранённый шаблон пресета `composition` через дропдаун применяется частично: пресет
  переключается, но `criteria.metric`/`criteria.period` не подхватываются — таблица
  показывает строки прежнего пресета. Бэкенд при этом отдаёт шаблон корректно (через
  API `/reports/templates` поля `metric`/`period` в JSON присутствуют).
- Скорее всего race в `applyTemplate` / `watch(preset)` в `frontend/src/views/ReportsView.vue`:
  одновременная установка `preset.value` (триггерит watch → runPreview) и
  `criteria.metric` приводит к тому, что первый runPreview уходит без metric. Прямой
  drill-down с дашборда (`?preset=composition&metric=...&period=...`) работает.
- **Срок:** ~30 минут. **Fix:** перед `preset.value = ...` собрать всё criteria сразу;
  либо `await nextTick()` между этапами; либо подавить watch при programmatic apply.

### DocType.CORRECTION в основном enum 🆕
- Сейчас Корректировки долга/реализации парсятся как `doc_type='correction'` в

### Intra-source дубли в payments.xls (особенно ПРОМСТРОЙХОЛДИНГ)
- В payments.xls встречаются группы документов с одинаковыми `(org, date, amount)` и идентичным
  `raw_name` (317 групп по БД). В большинстве это **разные реальные платежи** на одну сумму
  в один день (разные счета, договоры — видно по `raw_name`). Но Софья указала, что у
  ПРОМСТРОЙХОЛДИНГА (ИНН 5018126839) реально ~234K ₽, а в системе ₽468 512 — точно 2×.
  Скорее всего, бухгалтер импортировал `payments.xls` дважды в один день.
- **Что делать:** написать запрос на детект intra-source дублей с одинаковым `raw_name` И
  одинаковым `import_run_id` (если бывают). Или проверить нет ли ImportRun-ов с одним и тем же
  `file_hash` — это сигнал двойного импорта.
- **Срок:** 1-2 часа.

## Безопасность

### Rate-limiting / fail2ban на nginx
- В логах backend постоянные bot-сканы на `.env`, `.git/config`, `phpunit`.
- Это шум, но открывает риск brute-force на `/auth/login`.
- Установить `nginx-limit-req-zone` + fail2ban для `/api/v1/auth/login` (5 попыток / минуту с IP).
- **Срок:** 1-2 часа.

### Закрыть `/docs` и `/openapi.json` в production
- Сейчас публично доступны. Они не показывают данные, но раскрывают всю схему API (помогает атакующим).
- FastAPI: `app = FastAPI(docs_url=None, openapi_url=None)` или прятать за basic-auth.
- Или сделать через env: показывать только при `DEBUG=true`.
- **Срок:** 30 минут.

### Audit log для админских операций
- Сейчас `create user`, `reset password`, `change role`, `delete` (если будет) не логируются отдельно.
- Минимум: писать в отдельную таблицу `audit_log(user_id, action, target, ts, ip)`.
- Полезно для compliance и расследований.
- **Срок:** 1 день.

### Ротация JWT secret
- `settings.SECRET_KEY` сейчас, вероятно, статичный. Проверить — если так, добавить процедуру ротации.
- При смене все токены инвалидируются — для 5 пользователей не проблема.
- **Срок:** 30 минут.

### Force password change on first login
- Когда admin создаёт пользователя через UI, сгенерированный пароль показывается один раз.
- Добавить флаг `must_change_password` — при логине пользователя сразу редиректить на `/profile`.
