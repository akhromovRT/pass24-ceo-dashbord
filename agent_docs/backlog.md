#### P3.0.5 — 🐛 Баг: оплата ООО «Веста» 87 150,70 ₽ не зачлась против долга
- **Софья:** «Не зачлась оплата с выписки 1С, хотя ООО Веста закрыли все долги с декабря 2025 г. по июнь 2026 г. общей суммой на 87 150,70».
- **Гипотеза:** один платёж 87150,70 ₽ должен был через FIFO разнестись на 7 monthly_charges (дек'25 + янв–июн'26 по ~12 450 ₽). Почему-то не разнёсся.
- **Возможные причины:**
  - `period_extraction` нашёл из назначения только один период (например, «июнь 2026») и AllocationService разнёс всё в июнь, не запустив FIFO по прошлому.
  - Платёж попал через bank_statement, а не payments_report; в bank-импорте может быть проблема с period_extraction.
  - AllocationService не пересобирает леджер после нового платежа.
- **План:** найти Веста в БД (`SELECT … WHERE name_1c ILIKE '%веста%'`), посмотреть Document c amount=87150.70, проверить `payment_allocations`. Затем починить логику.
- **Срок:** 2–4 ч (диагностика + fix + тест).
- **Зависимость:** связано с P3.0.10 (ручной зачёт).

#### P3.0.1 — Перформанс «1С-вида» по публичному интернету
- **Жалоба:** «Без VPN очень сильно тормозит данный интерфейс, иногда время ожидания достигает минуты».
- **Корень:** `/api/v1/debt-snapshots/latest` отдаёт целиком все ~6 тыс. строк snapshot'a + 297 actual_org_totals + workflow_by_org + diffs. На боевом файле это ~3–5 MB JSON, в проде без gzip и без HTTP/2 это даёт минуту ожидания на 4G/мобильном.
- **Fix (по эскалации эффорта):**
  - **(а)** Включить `gzip on` в `frontend/nginx.conf` для `application/json` (тип уже включён в стандартных profiles, проверить — возможно, не работает из-за `gzip_proxied off`). Ожидаемый выигрыш 5–10× по размеру.
  - **(б)** Включить HTTP/2 (если ещё не) — `listen 443 ssl http2;` в nginx-блоке.
  - **(в)** Server-side кеш `/debt-snapshots/latest` по `snapshot.id` (snapshot immutable между импортами): простой `lru_cache` на N минут или `Cache-Control: max-age=300` на ответ + `ETag = snapshot.id`. После применения миграции данные не меняются — кеш безопасен.
  - **(г)** На уровне ответа: не отдавать `rows` целиком, отдавать только buyer-уровень. Контракты/документы подгружать lazy при раскрытии узла TreeTable (отдельный GET `/debt-snapshots/{id}/rows?parent_row_id=...`).
- **Срок:** (а)+(б) — 30 минут (вероятно решат проблему). (в) — 1 час. (г) — 1 день (требует изменения фронта).
- **Зависимости:** нет.

### P3.2 — Прогноз MRR ✅ Базово закрыто 2026-05-28
В `/dashboard/mrr-trend?forecast_months=N` (default 12) возвращается история
+ прогноз. Прогноз — простая линейная регрессия по последним до 6 точкам
`paid_ap` (slope·t+intercept, clip от 0 снизу). Поле `forecast_paid_ap`
у будущих месяцев; `sold_ap`/`paid_ap = null` чтобы фронт мог рисовать
другой стиль линии. Unit-тесты — `test_mrr_forecast.py`.

**Что ещё доработать (отдельной итерацией):** учёт churn-rate в прогнозе
(сейчас игнорируется); три линии на графике (факт / план / прогноз) —
нужна правка `DashboardView.vue`, где MRR-trend рисуется через vue-echarts.

### Применение шаблона composition в /reports теряет metric/period
- Сохранённый шаблон пресета `composition` через дропдаун применяется частично: пресет
  переключается, но `criteria.metric`/`criteria.period` не подхватываются — таблица
  показывает строки прежнего пресета. Бэкенд при этом отдаёт шаблон корректно (через
  API `/reports/templates` поля `metric`/`period` в JSON присутствуют).
- Скорее всего race в `applyTemplate` / `watch(preset)` в `frontend/src/views/ReportsView.vue`:
  одновременная установка `preset.value` (триггерит watch → runPreview) и
  `criteria.metric` приводит к тому, что первый runPreview уходит без metric. Прямой
  drill-down с дашборда (`?preset=composition&metric=...&period=...`) работает.
- **Срок:** ~30 минут. **Fix:** перед `preset.value = ...` собрать всё criteria сразу;
  либо `await nextTick()` между этапами; либо подавить watch при programmatic apply.

### Intra-source дубли в payments.xls (особенно ПРОМСТРОЙХОЛДИНГ)
- В payments.xls встречаются группы документов с одинаковыми `(org, date, amount)` и идентичным

  Скорее всего, бухгалтер импортировал `payments.xls` дважды в один день.
- **Что делать:** написать запрос на детект intra-source дублей с одинаковым `raw_name` И
  одинаковым `import_run_id` (если бывают). Или проверить нет ли ImportRun-ов с одним и тем же
  `file_hash` — это сигнал двойного импорта.
- **Срок:** 1-2 часа.

## Безопасность

### Rate-limiting / fail2ban на nginx ✅ Частично закрыто 2026-05-28
В `/auth/login` встроен in-memory rate-limit (10 попыток / 60 сек с IP, 429
после превышения). Этого хватает для текущего масштаба (1 backend-инстанс,
5 пользователей). При горизонтальном масштабировании или росте brute-force
шума — заменить на slowapi/Redis. fail2ban на nginx — отдельной итерацией
если шум станет проблемой.

### Закрыть `/docs` и `/openapi.json` в production ✅ Закрыто 2026-05-28
В `Settings.DEBUG` (default `False`); `app.main` создаёт FastAPI с
`docs_url`/`redoc_url`/`openapi_url = None` если DEBUG не выставлен.
Чтобы временно открыть локально: `DEBUG=true` в `.env` backend.

### Audit log для админских операций ✅ Закрыто 2026-05-28
Таблица `audit_log` (миграция `e2c8f1a90d4b`), хелпер
`app.services.audit_service.write_audit`. Интегрирован в `users.create`
и `users.reset_password` (логируется actor email + детали + ip). Остальные
admin-операции (правка статуса org, attach/detach платежей и т.п.) — по
мере добавления, через тот же хелпер.

### Ротация JWT secret 🚧 Не закрыто
Требует ручного изменения `.env` SECRET_KEY на сервере + рестарт backend
(все токены инвалидируются — пользователи перелогинятся). Процедура простая,
но требует action от admin. Рекомендация: документировать в `runbook.md` и
делать раз в полгода / при подозрении на компрометацию.

### Force password change on first login ✅ Закрыто 2026-05-28
Поле `User.must_change_password` (миграция `d9f4a7b2c5e8`), ставится в
`true` при создании через UI с сгенерированным паролем и при
`reset-password`. `/auth/me` возвращает флаг — фронт должен редиректить
