### 2026-05-28 — Offsite-бэкап БД в TimeWeb S3 подключён

**Контекст:** до сегодняшнего дня было две точки бэкапа — `/srv/ceo24/backups/` на сервере (ретеншн 14 дней) и зеркало `~/Backups/ceo24/` на ноуте (pull в 05:00 launchd). Backlog'овый пункт «бэкап в S3» (Yandex рассматривался ранее) закрыт переходом на TimeWeb Cloud S3 — заказчик предоставил бакет `pass24-backups` (endpoint `https://s3.twcstorage.ru`, регион `ru-1`).

**Что сделано:**
- На сервере поставлен `aws-cli/2.34.55` (официальный bundle, не deb — в Ubuntu 24.04 пакета нет).
- Создан `/etc/ceo24/backup-s3.env` с ключами TimeWeb (root:root, chmod 600). Шарится бакет с чужим `wordpress/`-префиксом, наши дампы изолированы под `ceo24/`.
- Доработан `/usr/local/bin/ceo24-backup.sh`: после успешного локального дампа выполняется `aws s3 cp` в `s3://pass24-backups/ceo24/`. Ошибка S3 не валит скрипт — локальный бэкап уже сохранён, в лог пишется `ERROR s3:`.
- Ретеншн на S3 — 30 дней (длиннее локальных 14, чтобы покрыть «локально сломалось N дней назад»). Чистка — самим скриптом по `LastModified` через `s3api list-objects-v2`, **не** lifecycle policy на бакет (там чужие данные).
- Старая версия скрипта сохранена как `/usr/local/bin/ceo24-backup.sh.bak-2026-05-28`.

**Проверка:** ручной запуск `ceo24-backup.sh` → лог `OK local: ...3695799 bytes` + `OK s3: s3://pass24-backups/ceo24/ceo24-2026-05-28-1056.dump.gz`, в бакете объект 3.5 MiB виден.

**Документация:** `runbook.md` обновлён (новая строка в таблице доступов, секция «восстановление из S3», список файлов на сервере). Пункт в `backlog.md` помечен ✅ закрыто.

**Следующий шаг:** ротировать ключи TimeWeb в их панели (исходные ключи попали в транскрипт сессии) и обновить `/etc/ceo24/backup-s3.env`. Через сутки убедиться, что cron в 03:00 UTC отработает S3-копию без вмешательства.

### 2026-05-27 — Этап 3: UI «1С-вид» в разделе «Должники» + сверка с БД

**Контекст:** этап 3 пятиэтапного плана работы с импортом 1С. Цель — дать CEO/бухгалтерии возможность открыть конкретный импорт «как в Excel-файле 1С» и быстро убедиться, что вся информация разнеслась правильно по клиентам.

**Что сделано:**
- **Backend** `backend/app/api/v1/debt_snapshots.py` (зарегистрирован в `main.py`):
  - `GET /debt-snapshots` — мета-список всех снимков (новейшие сверху), для дропдауна.
  - `GET /debt-snapshots/latest` — последний снимок + все строки + сверка с БД.
  - `GET /debt-snapshots/{id}` — конкретный снимок.
  - Сверка с БД: для каждой buyer-строки с `organization_id` сравнивается `DebtSnapshotRow.debt_end` (файл 1С) с `Organization.total_debt` (текущая БД). Расхождения > 1 ₽ возвращаются массивом `diffs` (исключая клиентов с `excluded_from_analytics=True`). При этом ниже buyer'а в дереве (contract/document) — те же rows из snapshot, без отдельной сверки, потому что в основной БД нет сумм на уровне contract/document.
- **Frontend** `frontend/src/views/DebtorsView.vue`:
  - `SelectButton` сверху: «Реестр должников» (старый вид) ↔ «1С-вид» (новый). Режим живёт в `route.query.mode`, чтобы можно было поделиться ссылкой.
  - В «1С-виде»:
    - `Select` для выбора импорта (latest по умолчанию, в дропдауне filename + период + дата импорта).
    - `InputText` глобальный поиск по имени/ИНН/№ документа/№ договора — фильтрует TreeTable с авто-раскрытием подходящих веток.
    - Toggle «Только расхождения» — показывает только buyers с `has_diff` и их детей.
    - `SegmentBand` со сводкой: Долг по файлу, Аванс по файлу, кол-во покупателей, кол-во расхождений.
    - `TreeTable` (PrimeVue) с тремя уровнями: Покупатель → Договор → Документ. 10 колонок 1-в-1 как в Excel (ИНН/№ + 8 числовых полей).
    - Расхождения подсвечиваются: тёмно-красное имя + Tag «≠ БД» рядом со строкой buyer.
  - Иерархия строится на клиенте из flat-списка с `parent_row_id` (один SQL-запрос на бэке, дерево складывается на фронте — быстрее).

- **Bugfix этапа 2**: `_build_debt_snapshot._sum` возвращал `Decimal(0) or None == None` для всех нулевых сумм. Заменил на честный track-seen — теперь 0 (есть данные, сумма 0) и None (поле не заполнено ни у одного buyer) различаются.

**Тесты:** добавлено 4 API-теста (`test_debt_snapshots_api.py`): список снимков, latest, 404 для пустой БД, обнаружение расхождений при искусственном дрейфе `Organization.total_debt`. Полный suite — 245 passed, 0 failed.

### 2026-05-27 — Этап 2: модель DebtSnapshot и сохранение полного среза 1С при импорте

**Контекст:** этап 2 пятиэтапного плана работы с импортом 1С. Цель — на каждый импорт файла «Задолженность покупателей» сохранять полный срез: Покупатель → Договор → Документ × все 8 числовых колонок (Долг/Аванс на начало/конец, Продано/Оплачено, Поступило/Зачтено предоплата). Это нужно для UI «1С-вид» (этап 3) и автосверки (этап 4); в основной модели Organization/Contract/Document авансы и предоплаты не хранятся.

**Что сделано:**
- **Новые таблицы** `debt_snapshots` и `debt_snapshot_rows` (`backend/app/models/debt_snapshot.py`):
  - `DebtSnapshot`: 1-к-1 с `ImportRun` (для debt-импорта). Хранит filename, период, агрегированные итоги по всем 8 колонкам, счётчики (buyers/contracts/documents/buyers_no_inn).
  - `DebtSnapshotRow`: одна запись на каждую строку файла (buyer/contract/document). Поля `parent_row_id` (для иерархии) + `row_index` (для сохранения порядка из файла) + все 8 числовых полей + опциональные FK на `Organization` / `Contract` / `Document` для сопоставления с реальными сущностями БД.
- **Миграция Alembic** `a3f1b9c47e02_add_debt_snapshots.py` (head: `d8e2b91f5a7c → a3f1b9c47e02`). Включая enum `debtsnapshotlevel`, CASCADE на удаление snapshot/import_run и SET NULL на удаление organization/contract/document.
- **Интеграция в `import_service.process_import`**:
  - При обходе buyers/contracts/documents запоминаются сопоставления `id(parsed_obj) → созданная сущность БД`.
  - После основной обработки вызывается `_build_debt_snapshot(...)` — пишет `DebtSnapshot` + дерево `DebtSnapshotRow` в той же транзакции (commit вместе с import_run).
  - Физлица без ИНН: в `Organization` не пишутся (UNIQUE на inn), но в `DebtSnapshot` сохраняются полностью с `organization_id=NULL`. Аналогично — все 8 колонок сохраняются вне зависимости от того, удалось ли сопоставить строку.
  - `_process_document` распилен на `_build_document` (создаёт объект Document) + `_add_document` (делает dedup) — чтобы получить ссылку на созданный документ для записи в snapshot row.
- **Backfill-скрипт** `backend/scripts/backfill_debt_snapshot.py`: для существующего `ImportRun` парсит исходный файл и создаёт `DebtSnapshot` ретроспективно. Используется одноразово для последнего импорта (1a9b0b7a от 26.05) — обычные импорты после деплоя пишут snapshot автоматически.

**Сохраняемые поля в snapshot row** (раньше терялись):
- `advance_start` / `advance_end` (аванс клиентов — ~6.9 млн ₽ в текущем файле, нигде не учитывался);

### 2026-05-26 — Этап 1 фикса парсера задолженности: 188 → 0 ошибок

**Контекст:** CEO запросил новое представление «как в файле 1С» в разделе «Должники» для сверки импорта. При исследовании файла `Задолженность покупателей за 01.01.2025 - 24.05.2026.xls` обнаружили, что текущий парсер `debt_report.py` падает с **188 ошибками** на 6058 строках — теряются документы и контракты. Принят 5-этапный план реализации; это запись по этапу 1 (фикс парсера, без нового UI).

**Что было пропущено в исходном парсере:**
- Период в формате «за DD.MM.YYYY - DD.MM.YYYY» (был только формат с русскими месяцами).
- Служебный маркер раскрытия группы 1С `<...>` — 27 строк выдавали ошибку.
- `Корректировка долга / Корректировка реализации` (14 шт) — не распознавались как DOCUMENT.
- Допсоглашения с разным написанием: `Доп. согл.`, `Доп.согл.`, `Доп согл`, `Доп сог.` — 7 шт.
- Договоры без префикса «Договор»: `0ББП-000045 от ...`, `Альфа 2021/05-1089/П от ...`, `№2025/01-1007/Р от ...`, `№ 24/02 - 2025 от ...`.
- Договоры без даты: `№2021/03-1055/СКУД`.
- `ГРАЖДАНСКО-ПРАВОВОЙ ДОГОВОР (Контракт) №...` — слово «договор» не в начале строки.
- `Без договора`, `счет-оферта` со строчной (case-sensitive prefix-матч).
- Физлица без ИНН в колонке B: АФАНАСЬЕВ, ГОЙДА, ГОРШКОВА, Карташев, КАШИН, ЛЮТИК, РЕУТОВА — 7 шт.

**Что сделано (`backend/app/parser/debt_report.py`):**
- Новый `_PERIOD_RE_DATES` (даты) + fallback на `_PERIOD_RE_MONTHS` (месяцы).
- `HierarchyLevel.GROUP_MARKER` + skip в основном цикле без записи в `errors`.
- `_detect_doc_type`: добавлены `correction`, `writeoff`, `refund` (Возврат товаров, Списание задолженности).
- `_normalize_contract_name`: единая нормализация всех написаний «Доп* сог*» к «Допсоглашение».
- `_CONTRACT_PREFIXES` переведён в lower-case + `name.lower()` для case-insensitive сравнения.
- `_BARE_CONTRACT_RE` расширен: поддержка кириллицы и пробела между словом и номером в начале строки.
- `_CONTAINS_DOGOVOR_RE`: распознавать договор по слову «договор» в любом месте строки.
- `_PERSON_NAME_RE`: ФИО без ИНН → `HierarchyLevel.BUYER` (только кириллица/пробелы/_-).
- `process_import` в `import_service.py`: физлица без ИНН — `continue` (не падаем по UNIQUE), счётчик `skipped_buyers_no_inn` в `delta_summary`. Полноценное сохранение этих покупателей будет в этапе 2 через `DebtSnapshot`.

**Результат на боевом файле 24.05.2026:**
- Ошибок: **188 → 0** (7 физлиц без ИНН распознаются как BUYER, но пропускаются импорт-сервисом).
- Покупателей: 290 ЮЛ + 7 ФЛ = 297 (раньше теряли 7 ФЛ).
- Контрактов: 407 → **447** (+40 благодаря допсоглашениям и нестандартным номерам).
- Документов: 5164 → **5278** (+114 — корректировки, документы под потерянными контрактами).
- Период: парсится `2025-01-01 → 2026-05-24`.
- Итого по файлу: долг 5 826 935 ₽, аванс 6 918 262 ₽ (раньше аванс терялся полностью).

### 2026-05-26 — Шахматка: календарный год + ушедшие клиенты + поиск + сортировка
