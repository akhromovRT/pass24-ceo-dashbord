### 2026-05-29 — 🐛 Багфикс: оплата ООО «Веста» 87 150,70 ₽ не разносилась против долга

**Контекст:** Софья в личке (#96538): «Не зачлась оплата с выписки 1С, хотя ООО Веста закрыли все долги с декабря 2025 г. по июнь 2026 г. общей суммой на 87 150,70». Расследование показало, что парсер банк-выписки корректно разбил один входящий платёж на 7 Document с правильными `period_year/period_month` (дек'25 + янв–июн'26), но `AllocationService` их полностью игнорировал — `total_debt` Весты так и остался 61 763,80 ₽.

**Корневых причин две (`9d300f9`):**

1. **`AllocationService._payments` фильтровал по `Contract.contract_number == '1C-PAYMENTS'`**, полностью игнорируя `BANK-IMPORT` платежи. Исторически это была защита от cross-source дублей (см. ADR-018), но после 2026-05-28 добавлен dedup на этапе импорта банка — банк-копии теперь создаются только если их нет в реестре 1С. То есть «защита через игнорирование» стала вредной — теперь безопасно разносить и банк-платежи. **Fix:** убрал фильтр по `contract_number`, `_payments` берёт PAYMENT-документы из любых контрактов.
2. **Поля `payment.period_year/period_month` использовались только при `period_manual=True`**. Банк-парсер ставит `period_manual=False` (это автоматический парсинг, не ручной ввод), поэтому AllocationService падал на regex-вытягивание периодов из `raw_name`, который для строки «...за период декабрь 2025 — июнь 2026...» возвращает только `[(2025, 12), (2026, 6)]` — границы диапазона, не все 7 месяцев. **Fix:** структурированное поле `period_year/period_month` приоритетнее regex — берём независимо от `period_manual`.

**Recompute:** прогнан для всех 445 организаций (через `nohup` в фоне) — 101 клиент с нерасnесёнными банк-платежами → 0. Аллокаций было 14 075 → стало 14 559 (+484).

**По Весте конкретно:** 6 charges (дек'25 – май'26) закрыты полностью, остаток 9 286,55 ₽ ушёл в ADVANCE за июнь (charge ещё не сгенерирован, придёт после ближайшего импорта от Ирины). **Но:** `Organization.total_debt` всё ещё показывал старое значение 61 763,80 ₽ — это денормализованное поле, которое обновлялось только при импорте debt-report'а. Это породило отдельный пункт P3.0.5.1 (см. запись выше).

**Регресс-тест:** `test_bank_parser_filled_period_used_without_period_manual` — 7 платежей с `period_y/m+manual=False`, 6 charges; проверяем что все 6 закрыты полностью (сумма аллокаций == сумма charges). До fix'а — 0 аллокаций. Тесты: 258 → 259.

### 2026-05-27 — Этап 2: модель DebtSnapshot и сохранение полного среза 1С при импорте

**Контекст:** этап 2 пятиэтапного плана работы с импортом 1С. Цель — на каждый импорт файла «Задолженность покупателей» сохранять полный срез: Покупатель → Договор → Документ × все 8 числовых колонок (Долг/Аванс на начало/конец, Продано/Оплачено, Поступило/Зачтено предоплата). Это нужно для UI «1С-вид» (этап 3) и автосверки (этап 4); в основной модели Organization/Contract/Document авансы и предоплаты не хранятся.

**Что сделано:**
- **Новые таблицы** `debt_snapshots` и `debt_snapshot_rows` (`backend/app/models/debt_snapshot.py`):
  - `DebtSnapshot`: 1-к-1 с `ImportRun` (для debt-импорта). Хранит filename, период, агрегированные итоги по всем 8 колонкам, счётчики (buyers/contracts/documents/buyers_no_inn).
  - `DebtSnapshotRow`: одна запись на каждую строку файла (buyer/contract/document). Поля `parent_row_id` (для иерархии) + `row_index` (для сохранения порядка из файла) + все 8 числовых полей + опциональные FK на `Organization` / `Contract` / `Document` для сопоставления с реальными сущностями БД.
- **Миграция Alembic** `a3f1b9c47e02_add_debt_snapshots.py` (head: `d8e2b91f5a7c → a3f1b9c47e02`). Включая enum `debtsnapshotlevel`, CASCADE на удаление snapshot/import_run и SET NULL на удаление organization/contract/document.
- **Интеграция в `import_service.process_import`**:
  - При обходе buyers/contracts/documents запоминаются сопоставления `id(parsed_obj) → созданная сущность БД`.
  - После основной обработки вызывается `_build_debt_snapshot(...)` — пишет `DebtSnapshot` + дерево `DebtSnapshotRow` в той же транзакции (commit вместе с import_run).
  - Физлица без ИНН: в `Organization` не пишутся (UNIQUE на inn), но в `DebtSnapshot` сохраняются полностью с `organization_id=NULL`. Аналогично — все 8 колонок сохраняются вне зависимости от того, удалось ли сопоставить строку.
  - `_process_document` распилен на `_build_document` (создаёт объект Document) + `_add_document` (делает dedup) — чтобы получить ссылку на созданный документ для записи в snapshot row.
- **Backfill-скрипт** `backend/scripts/backfill_debt_snapshot.py`: для существующего `ImportRun` парсит исходный файл и создаёт `DebtSnapshot` ретроспективно. Используется одноразово для последнего импорта (1a9b0b7a от 26.05) — обычные импорты после деплоя пишут snapshot автоматически.
