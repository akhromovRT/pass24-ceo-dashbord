# ADR

## Записи

### ADR-001: Монолитная архитектура вместо микросервисов

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** При 274 клиентах и 5 пользователях нагрузка минимальна. Команда 1-2 разработчика.
**Решение:** Монолит: FastAPI + PostgreSQL + Vue 3. Один сервер, один деплой.
**Последствия:** Простота разработки и деплоя. При росте до 1000+ клиентов — выделить парсер и алерты в отдельные сервисы.

### ADR-002: SQLModel вместо SQLAlchemy + Pydantic отдельно

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** FastAPI использует Pydantic для валидации, SQLAlchemy — для ORM. SQLModel объединяет оба.
**Решение:** SQLModel — одна модель = и ORM, и схема API. Миграции через Alembic.
**Последствия:** Меньше дублирования кода. Автор SQLModel и FastAPI один (Sebastián Ramírez).

### ADR-003: Иммутабельные снапшоты

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** Нужна возможность сравнивать данные за любые два периода, аудируемость импорта.
**Решение:** Каждый импорт создаёт новый snapshot в `monthly_snapshots`. Данные не перезаписываются.
**Последствия:** Рост объёма БД (~3KB × 274 клиента × 12 месяцев = ~10MB/год). Полная трассируемость изменений.

### ADR-004: Три источника данных вместо одного

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** Спецификация описывала один источник (Задолженность покупателей). Реально используются три файла: задолженность, банковская выписка, аналитика поступлений.
**Решение:** Три парсера: (1) задолженность — 3-уровневая иерархия, (2) выписка — плоский список платежей, (3) аналитика — начальная загрузка метаданных (объекты, адреса, ссылки на облако, план/факт).
**Последствия:** Более полная модель данных. Файл аналитики используется для первичной миграции, затем данные обогащаются через UI.

### ADR-005: Расширенная модель organizations

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** Текущая таблица аналитики содержит поля, отсутствующие в спецификации: объекты, тип объекта, ссылка на облако PASS24, № в системе, адрес, город/область.
**Решение:** Добавить поля в модель `organizations`: objects, object_type, cloud_url, system_number, equipment, address, city_region.
**Последствия:** Полнее заменяет текущую Excel-таблицу. UI карточки клиента содержит всю необходимую информацию.

### ADR-006: uv для управления Python-окружением

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** На машине macOS-системный Python 3.9.6. Проект требует Python 3.12. `pip` недоступен, `pyenv` не установлен. `uv` уже установлен через Homebrew и имеет Python 3.12.12.
**Решение:** Использовать `uv` для создания venv (`uv venv --python 3.12`) и установки зависимостей (`uv pip install`). Venv хранится в `backend/.venv`.
**Последствия:** Быстрая установка зависимостей (Rust-based resolver). Совместим со стандартным pip/venv workflow. Docker-образ продолжает использовать `pip install` напрямую.

### ADR-007: Docker без named volumes (Timeweb)

**Дата:** 2026-03-07
**Статус:** Superseded by ADR-010 (2026-05-13)
**Контекст:** Предполагалось, что Timeweb managed platform запрещает `volumes` в docker-compose.yml. При деплое 2026-03-07 наблюдалась ошибка «volumes is not allowed».
**Решение:** Убрать все volumes (pgdata, nginx.conf bind mount). Nginx config копируется в образ через `COPY nginx.conf` в frontend/Dockerfile. PostgreSQL данные хранятся внутри контейнера (для MVP приемлемо).
**Последствия:** Данные БД теряются при пересоздании контейнера. Для production — добавить managed PostgreSQL или external volume. Nginx config меняется через rebuild образа.
**Почему superseded:** При диагностике 2026-05-13 выяснилось, что хост — обычный Ubuntu 24.04 VPS, не managed Apps. Bind mount работает без ограничений. См. ADR-010.

### ADR-008: xlrd для поддержки .xls (OLE2)

**Дата:** 2026-03-07
**Статус:** Принято
**Контекст:** 1С экспортирует файлы в .xls (старый формат OLE2). openpyxl поддерживает только .xlsx (OpenXML).
**Решение:** Утилита `load_workbook_any()` в `parser/utils.py`: определяет формат по расширению, для .xls загружает через xlrd и конвертирует в openpyxl Workbook в памяти.
**Последствия:** Прозрачная поддержка обоих форматов. Конвертация in-memory (без временных файлов). Зависимость: xlrd>=2.0.

### ADR-009: Режим-переключатель в реестре клиентов

**Дата:** 2026-03-07
**Статус:** Принято
**Контекст:** Реестр должен показывать как обзор по клиентам (org-level), так и детальный вид по договорам (contract-level с 11+ полями). Два отдельных раздела — лишняя навигация.
**Решение:** SelectButton "По клиентам" / "По договорам" в BillingView. Общие поиск и pagination, разные DataTable. Клик по строке в обоих режимах ведёт на карточку клиента.
**Последствия:** Один URL, два представления. Серверная пагинация и сортировка для обоих режимов. Новый endpoint `GET /api/v1/contracts` с join Contract+Organization.

### ADR-010: PostgreSQL persistence через bind mount на хосте

**Дата:** 2026-05-13
**Статус:** Принято
**Контекст:** ADR-007 (без volumes) основывался на ошибочной посылке о managed Apps-окружении Timeweb. После инцидента 2026-05-13 (28-дневный downtime + Exit 255) проведена диагностика: хост — обычный Ubuntu 24.04 VPS, никаких ограничений на volumes. Параллельно решено не переходить на managed PostgreSQL по соображениям бюджета.
**Решение:** PostgreSQL хранит данные в bind mount `/srv/ceo24/pgdata` на хосте. Каталог создан вне рабочей директории проекта (`/root/pass24-ceo-dashbord/`), что делает данные независимыми от `git pull` и пересоздания compose. Владелец — uid 70 (postgres в alpine), права 700. Проверено: `docker compose rm -fs db && up -d db` → данные остаются на месте.
**Последствия:** Пересоздание контейнера `db` (ребилд, обновление образа, миграция) не теряет данные. Бэкап выполняется отдельно через cron + `pg_dump -Fc` (см. `/usr/local/bin/ceo24-backup.sh` на сервере). ADR-007 помечен superseded.

### ADR-011: Router-level auth dependency

**Дата:** 2026-05-13
**Статус:** Принято
**Контекст:** Инцидент 2026-05-13: при диагностике обнаружено, что только `/auth` использует `Depends(get_current_user)`. Остальные роутеры (dashboard, billing, organizations, contracts, alerts, imports) принимают `Depends(get_session)` без проверки токена. Все финансовые данные ОНВИ СЕРВИС были публично доступны через HTTP API.
**Решение:** Применить guard на уровне роутера: `APIRouter(prefix=..., dependencies=[Depends(get_current_user)])`. Это закрывает все эндпоинты роутера одной строкой и устойчиво к забывчивости при добавлении новых эндпоинтов.
**Последствия:** Auth обязателен для всех data-эндпоинтов. `/auth/login`, `/health`, `/docs`, `/openapi.json` остаются открытыми (нужны для UX и health-check). Тесты с TestClient переопределяют `get_current_user` через `app.dependency_overrides`.

### ADR-012: AR-леджер — учёт абонплаты через начисления и аллокацию платежей

**Дата:** 2026-05-18
**Статус:** Принято
**Контекст:** Метрика собираемости (`collection-trend`) сравнивала валовой приток платежей по дате прихода с планом одного месяца. Платежи приходят неравномерно (за прошлые / текущий / будущие периоды), поэтому метрика искажена (март 2026 — мнимые 127%).
**Решение:** Учёт по принципу дебиторского леджера. Три таблицы: `tariff_periods` (история тарифа), `monthly_charges` (месячное начисление = абонплата), `payment_allocations` (разнесение платежа на одно или несколько начислений). Начисление закрытого месяца берётся из реальной 1С-Реализации (subscription-`SALE`), иначе — синтетика из тарифа. Платежи (реестр «Оплата от покупателей» из 1С) разносятся детерминированным движком: явный период из назначения → FIFO от старых долгов → аванс в будущие месяцы (горизонт 24 мес). Пересчёт клиента — чистая функция от (начисления, платежи, ручные правки).
**Последствия:** Собираемость месяца = (аллокации на начисления месяца) ÷ (начисления месяца) — корректна независимо от даты прихода денег. Появляется структура поступлений (текущее / аванс / погашение долга / непериодические). Источник платежей для леджера — синтетический контракт `1C-PAYMENTS` (отдельно от банк-выписки, чтобы не задвоить 2026). Ручные правки аллокаций (`is_manual`) сохраняются при пересчёте.

### ADR-013: Модуль «Отчёты» — пресеты, приоритет взыскания, сохраняемые шаблоны

**Дата:** 2026-05-19
**Статус:** Принято
**Контекст:** Нужен инструмент, где руководитель сам собирает выборку по критериям и выгружает её, с фокусом на снижение задолженности и рост собираемости. Готового экспорта в проекте не было.
**Решение:** Два пресета вместо одного универсального конструктора — `debtors` (реестр должников: кого взыскивать) и `discipline` (дисциплина платежей: кто соскальзывает в долг). Общая панель критериев (период, статус, менеджер, корзина, тип договора, город, мин. долг, колонки, сортировка). Отчёт собирается в `report_service.py` поверх AR-леджера (ADR-012) — отдельных таблиц-агрегатов нет, всё считается на лету из `monthly_charges`/`payment_allocations`. Введена вычисляемая метрика **приоритет взыскания** = `долг × (1 + min(months_overdue,12)×0.15) × (0.3 + 0.7×payment_score/100)` — ранжирует должников по «крупный × старый × возвратный». Экспорт — `.xlsx` через openpyxl (зависимость уже была). Наборы критериев сохраняются в таблице `report_templates` (`criteria` — JSON-колонка), шаблоны общие для всех пользователей.
**Последствия:** Новый эндпоинт-слой `/reports/*` (preview JSON + export .xlsx + CRUD шаблонов). Метрики отчётов согласованы с дашбордом, т.к. используют тот же леджер. Приоритет взыскания — эвристика, веса при необходимости уточняются в `report_service.py`. Структура доходов как третий пресет в v1 не делалась (есть на дашборде) — кандидат на развитие.

### ADR-014: HTTPS через Let's Encrypt, TLS-терминация в nginx-контейнере

**Дата:** 2026-05-19
**Статус:** Принято
**Контекст:** Подключён домен `ceo.pass24pro.ru`. Сервис работал по голому HTTP — JWT-логины и финансовые данные ОНВИ СЕРВИС передавались по открытому каналу. Нужен HTTPS без усложнения стека (один VPS, 5 пользователей).
**Решение:** TLS терминируется в уже существующем `frontend`-контейнере (nginx) — отдельный reverse-proxy не вводится. Сертификат — Let's Encrypt, хранится в bind mount `/srv/ceo24/certbot/{conf,www}` на хосте (тот же приём, что и `pgdata` — ADR-010), монтируется в контейнер read-only. Первичный выпуск — `certbot --standalone` (кратковременная остановка frontend ради порта 80). Продление — `certbot certonly --webroot` (nginx отдаёт `/.well-known/acme-challenge/` из bind mount), еженедельно через host-cron `/etc/cron.d/ceo24-cert-renew` + скрипт `/usr/local/bin/ceo24-cert-renew.sh` (по образцу `ceo24-backup.sh`). HTTP редиректит на HTTPS (301), включён HSTS.
**Последствия:** Весь трафик шифрован. Конфиг nginx собран в образ (иммутабелен), сертификат лежит на хосте (переживает ребилд и `git pull`). `certonly --keep-until-expiring` делает cron-продление идемпотентным — скрипт безопасно запускать часто. Заодно исправлен healthcheck `frontend`: `localhost` → `127.0.0.1` (`localhost` резолвился в IPv6 `::1`, nginx слушает только IPv4 — контейнер висел `unhealthy`). Прямой доступ по IP даёт предупреждение о несовпадении имени сертификата — приемлемо, канонический адрес — домен. HTTP-порт 80 оставлен открытым для ACME-проверки.
