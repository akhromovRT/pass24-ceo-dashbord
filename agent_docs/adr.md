### ADR-001: Монолитная архитектура вместо микросервисов

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** При 274 клиентах и 5 пользователях нагрузка минимальна. Команда 1-2 разработчика.
**Решение:** Монолит: FastAPI + PostgreSQL + Vue 3. Один сервер, один деплой.
**Последствия:** Простота разработки и деплоя. При росте до 1000+ клиентов — выделить парсер и алерты в отдельные сервисы.

### ADR-002: SQLModel вместо SQLAlchemy + Pydantic отдельно

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** FastAPI использует Pydantic для валидации, SQLAlchemy — для ORM. SQLModel объединяет оба.
**Решение:** SQLModel — одна модель = и ORM, и схема API. Миграции через Alembic.
**Последствия:** Меньше дублирования кода. Автор SQLModel и FastAPI один (Sebastián Ramírez).

### ADR-003: Иммутабельные снапшоты

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** Нужна возможность сравнивать данные за любые два периода, аудируемость импорта.
**Решение:** Каждый импорт создаёт новый snapshot в `monthly_snapshots`. Данные не перезаписываются.
**Последствия:** Рост объёма БД (~3KB × 274 клиента × 12 месяцев = ~10MB/год). Полная трассируемость изменений.

### ADR-004: Три источника данных вместо одного

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** Спецификация описывала один источник (Задолженность покупателей). Реально используются три файла: задолженность, банковская выписка, аналитика поступлений.
**Решение:** Три парсера: (1) задолженность — 3-уровневая иерархия, (2) выписка — плоский список платежей, (3) аналитика — начальная загрузка метаданных (объекты, адреса, ссылки на облако, план/факт).
**Последствия:** Более полная модель данных. Файл аналитики используется для первичной миграции, затем данные обогащаются через UI.

### ADR-005: Расширенная модель organizations

**Контекст:** Текущая таблица аналитики содержит поля, отсутствующие в спецификации: объекты, тип объекта, ссылка на облако PASS24, № в системе, адрес, город/область.

### ADR-006: uv для управления Python-окружением

**Дата:** 2026-03-04
**Статус:** Принято
**Контекст:** На машине macOS-системный Python 3.9.6. Проект требует Python 3.12. `pip` недоступен, `pyenv` не установлен. `uv` уже установлен через Homebrew и имеет Python 3.12.12.
**Решение:** Использовать `uv` для создания venv (`uv venv --python 3.12`) и установки зависимостей (`uv pip install`). Venv хранится в `backend/.venv`.
**Последствия:** Быстрая установка зависимостей (Rust-based resolver). Совместим со стандартным pip/venv workflow. Docker-образ продолжает использовать `pip install` напрямую.

### ADR-007: Docker без named volumes (Timeweb)

**Дата:** 2026-03-07
**Статус:** Superseded by ADR-010 (2026-05-13)
**Контекст:** Предполагалось, что Timeweb managed platform запрещает `volumes` в docker-compose.yml. При деплое 2026-03-07 наблюдалась ошибка «volumes is not allowed».
**Решение:** Убрать все volumes (pgdata, nginx.conf bind mount). Nginx config копируется в образ через `COPY nginx.conf` в frontend/Dockerfile. PostgreSQL данные хранятся внутри контейнера (для MVP приемлемо).
**Последствия:** Данные БД теряются при пересоздании контейнера. Для production — добавить managed PostgreSQL или external volume. Nginx config меняется через rebuild образа.
**Почему superseded:** При диагностике 2026-05-13 выяснилось, что хост — обычный Ubuntu 24.04 VPS, не managed Apps. Bind mount работает без ограничений. См. ADR-010.

### ADR-008: xlrd для поддержки .xls (OLE2)

**Дата:** 2026-03-07
**Статус:** Принято
**Контекст:** 1С экспортирует файлы в .xls (старый формат OLE2). openpyxl поддерживает только .xlsx (OpenXML).
**Решение:** Утилита `load_workbook_any()` в `parser/utils.py`: определяет формат по расширению, для .xls загружает через xlrd и конвертирует в openpyxl Workbook в памяти.

### ADR-009: Режим-переключатель в реестре клиентов

**Дата:** 2026-03-07
**Статус:** Принято
**Контекст:** Реестр должен показывать как обзор по клиентам (org-level), так и детальный вид по договорам (contract-level с 11+ полями). Два отдельных раздела — лишняя навигация.

### ADR-010: PostgreSQL persistence через bind mount на хосте

**Дата:** 2026-05-13
**Статус:** Принято
**Контекст:** ADR-007 (без volumes) основывался на ошибочной посылке о managed Apps-окружении Timeweb. После инцидента 2026-05-13 (28-дневный downtime + Exit 255) проведена диагностика: хост — обычный Ubuntu 24.04 VPS, никаких ограничений на volumes. Параллельно решено не переходить на managed PostgreSQL по соображениям бюджета.
**Решение:** PostgreSQL хранит данные в bind mount `/srv/ceo24/pgdata` на хосте. Каталог создан вне рабочей директории проекта (`/root/pass24-ceo-dashbord/`), что делает данные независимыми от `git pull` и пересоздания compose. Владелец — uid 70 (postgres в alpine), права 700. Проверено: `docker compose rm -fs db && up -d db` → данные остаются на месте.
**Последствия:** Пересоздание контейнера `db` (ребилд, обновление образа, миграция) не теряет данные. Бэкап выполняется отдельно через cron + `pg_dump -Fc` (см. `/usr/local/bin/ceo24-backup.sh` на сервере). ADR-007 помечен superseded.

### ADR-011: Router-level auth dependency

**Дата:** 2026-05-13
**Статус:** Принято
**Контекст:** Инцидент 2026-05-13: при диагностике обнаружено, что только `/auth` использует `Depends(get_current_user)`. Остальные роутеры (dashboard, billing, organizations, contracts, alerts, imports) принимают `Depends(get_session)` без проверки токена. Все финансовые данные ОНВИ СЕРВИС были публично доступны через HTTP API.
**Решение:** Применить guard на уровне роутера: `APIRouter(prefix=..., dependencies=[Depends(get_current_user)])`. Это закрывает все эндпоинты роутера одной строкой и устойчиво к забывчивости при добавлении новых эндпоинтов.
**Последствия:** Auth обязателен для всех data-эндпоинтов. `/auth/login`, `/health`, `/docs`, `/openapi.json` остаются открытыми (нужны для UX и health-check). Тесты с TestClient переопределяют `get_current_user` через `app.dependency_overrides`.

### ADR-012: AR-леджер — учёт абонплаты через начисления и аллокацию платежей

**Дата:** 2026-05-18
**Статус:** Принято
**Контекст:** Метрика собираемости (`collection-trend`) сравнивала валовой приток платежей по дате прихода с планом одного месяца. Платежи приходят неравномерно (за прошлые / текущий / будущие периоды), поэтому метрика искажена (март 2026 — мнимые 127%).
**Решение:** Учёт по принципу дебиторского леджера. Три таблицы: `tariff_periods` (история тарифа), `monthly_charges` (месячное начисление = абонплата), `payment_allocations` (разнесение платежа на одно или несколько начислений). Начисление закрытого месяца берётся из реальной 1С-Реализации (subscription-`SALE`), иначе — синтетика из тарифа. Платежи (реестр «Оплата от покупателей» из 1С) разносятся детерминированным движком: явный период из назначения → FIFO от старых долгов → аванс в будущие месяцы (горизонт 24 мес). Пересчёт клиента — чистая функция от (начисления, платежи, ручные правки).
**Последствия:** Собираемость месяца = (аллокации на начисления месяца) ÷ (начисления месяца) — корректна независимо от даты прихода денег. Появляется структура поступлений (текущее / аванс / погашение долга / непериодические). Источник платежей для леджера — синтетический контракт `1C-PAYMENTS` (отдельно от банк-выписки, чтобы не задвоить 2026). Ручные правки аллокаций (`is_manual`) сохраняются при пересчёте.

### ADR-013: Модуль «Отчёты» — пресеты, приоритет взыскания, сохраняемые шаблоны

**Дата:** 2026-05-19
**Статус:** Принято
**Контекст:** Нужен инструмент, где руководитель сам собирает выборку по критериям и выгружает её, с фокусом на снижение задолженности и рост собираемости. Готового экспорта в проекте не было.
**Решение:** Два пресета вместо одного универсального конструктора — `debtors` (реестр должников: кого взыскивать) и `discipline` (дисциплина платежей: кто соскальзывает в долг). Общая панель критериев (период, статус, менеджер, корзина, тип договора, город, мин. долг, колонки, сортировка). Отчёт собирается в `report_service.py` поверх AR-леджера (ADR-012) — отдельных таблиц-агрегатов нет, всё считается на лету из `monthly_charges`/`payment_allocations`. Введена вычисляемая метрика **приоритет взыскания** = `долг × (1 + min(months_overdue,12)×0.15) × (0.3 + 0.7×payment_score/100)` — ранжирует должников по «крупный × старый × возвратный». Экспорт — `.xlsx` через openpyxl (зависимость уже была). Наборы критериев сохраняются в таблице `report_templates` (`criteria` — JSON-колонка), шаблоны общие для всех пользователей.
**Последствия:** Новый эндпоинт-слой `/reports/*` (preview JSON + export .xlsx + CRUD шаблонов). Метрики отчётов согласованы с дашбордом, т.к. используют тот же леджер. Приоритет взыскания — эвристика, веса при необходимости уточняются в `report_service.py`. Структура доходов как третий пресет в v1 не делалась (есть на дашборде) — кандидат на развитие.

### ADR-014: HTTPS через Let's Encrypt, TLS-терминация в nginx-контейнере

**Дата:** 2026-05-19
**Статус:** Принято
**Контекст:** Подключён домен `ceo.pass24pro.ru`. Сервис работал по голому HTTP — JWT-логины и финансовые данные ОНВИ СЕРВИС передавались по открытому каналу. Нужен HTTPS без усложнения стека (один VPS, 5 пользователей).
**Решение:** TLS терминируется в уже существующем `frontend`-контейнере (nginx) — отдельный reverse-proxy не вводится. Сертификат — Let's Encrypt, хранится в bind mount `/srv/ceo24/certbot/{conf,www}` на хосте (тот же приём, что и `pgdata` — ADR-010), монтируется в контейнер read-only. Первичный выпуск — `certbot --standalone` (кратковременная остановка frontend ради порта 80). Продление — `certbot certonly --webroot` (nginx отдаёт `/.well-known/acme-challenge/` из bind mount), еженедельно через host-cron `/etc/cron.d/ceo24-cert-renew` + скрипт `/usr/local/bin/ceo24-cert-renew.sh` (по образцу `ceo24-backup.sh`). HTTP редиректит на HTTPS (301), включён HSTS.
**Последствия:** Весь трафик шифрован. Конфиг nginx собран в образ (иммутабелен), сертификат лежит на хосте (переживает ребилд и `git pull`). `certonly --keep-until-expiring` делает cron-продление идемпотентным — скрипт безопасно запускать часто. Заодно исправлен healthcheck `frontend`: `localhost` → `127.0.0.1` (`localhost` резолвился в IPv6 `::1`, nginx слушает только IPv4 — контейнер висел `unhealthy`). Прямой доступ по IP даёт предупреждение о несовпадении имени сертификата — приемлемо, канонический адрес — домен. HTTP-порт 80 оставлен открытым для ACME-проверки.

### ADR-015: Определение метрики «новый клиент» — клиент, впервые совершивший оплату

**Дата:** 2026-05-19
**Статус:** Принято
**Контекст:** Сверка отчёта продаж (Bitrix24, «Сводка по новым клиентам 2026.xlsx») с дашбордом CEO24 показала расхождение в счёте новых клиентов 2026 (14 у менеджеров против 21 на дашборде). Часть расхождения — разное определение «нового клиента»: менеджеры помечали «новыми» в том числе апсейл и новые объекты по уже платящим юрлицам (ЛАНИТ-ИНТЕГРАЦИЯ платит с 2021, Ассоциация «По-Рижская мечта» — с 2023, КСК «Битца» Москомспорта — с 2020).
**Решение:** Канон для всей системы и для отчётов продаж — новый клиент = юрлицо/ИП (идентифицируется по ИНН), совершившее **первую** оплату в рассматриваемом периоде. Технически — минимальная дата платёжного документа (`MIN(Document.doc_date)`, `doc_type=PAYMENT`) попадает в период. Допродажи и изменение абонплаты по уже платящим клиентам — это существующие активные клиенты, а не новые; в счётчике «новые клиенты» отчётов продаж они учитываться не должны. «Новый клиент» — основной KPI отдела продаж. Плитка дашборда «Новые за год» (`new_paid_curr_year`) уже реализует это определение.
**Последствия:** Дашборд и отчёты продаж используют единое определение. Метрики «Новые за год / за месяц» считаются по факту первой оплаты и не зависят от ручной разметки в CRM. Расхождение «отчёт менеджеров ↔ 1С» становится управленческим сигналом (пропущенные клиенты, ошибочная разметка апсейла как нового клиента). Ограничение: дашборд считает по ИНН и не отличает «новый объект существующего клиента» — для учёта новой выручки по апсейлу потребуется отдельный срез (кандидат на развитие). Операционное следствие — задача актуализации реестра (Bitrix24 №886, см. `backlog.md`).

### ADR-016: churn_month — остановка начислений АП после месяца отключения

**Дата:** 2026-05-21
**Статус:** Принято
**Контекст:** Клиент в статусе CHURNED («Отток») перестал быть нашим клиентом, но в существующей реализации `ChargeService` продолжает генерировать синтетические начисления из тарифа до текущего месяца. В результате долг такого клиента растёт каждый месяц, искажая дебиторку и метрики (общий долг, корзины старения), хотя по бизнес-смыслу мы не ждём от него оплаты. CEO явно сформулировал требование: с месяца отключения АП не начислять, в накопление долга не включать. Параллельное требование — не трогать выверенных активных клиентов.
**Решение:** Введено поле `Organization.churn_month: date | None` (хранится как 1-е число месяца, валидация в Pydantic). Поле учитывается **только** в `ChargeService.rebuild_for_organization` и **только** для клиентов в статусе CHURNED: `through = min(through, churn_month)`. Чтения (aging, dashboard, reports) не правились — они считают по существующим `monthly_charge`, которые после пересборки физически отсутствуют для месяцев после `churn_month`. Альтернатива «фильтровать на чтении» отвергнута: она создаёт «мёртвые» записи в БД, которые нужно отфильтровывать во всех будущих запросах. PATCH `/organizations` авто-проставляет `churn_month` месяцем последнего платежа при переходе ACTIVE → CHURNED; если платежей нет — 400 (бизнес-инвариант: клиента без платежей в базе быть не должно). При смене статуса/churn_month — ленивая пересборка `MonthlyCharge` + `PaymentAllocation` для одного клиента. Backfill — отдельный скрипт, идёт только по CHURNED-клиентам без `churn_month`; ACTIVE никогда не затрагивает.
**Последствия:** Чистая семантика: «нет начисления = нет долга». Активные клиенты гарантированно не задеты (двойная защита: фильтр статуса в коде ChargeService + backfill только по CHURNED). Аллокации платежей в месяцах после `churn_month` после пересборки переадресуются на ближайшие подходящие периоды через `AllocationService.recompute_for_organization` (overflow / FIFO). При возврате клиента в ACTIVE — `churn_month` очищается, лента пересобирается до `today`. Гранулярность «месяц» осознанно (не дата): абонплата помесячная, AR-леджер живёт в (year, month). Все UI с клиентом теперь показывают «Месяц отключения» в человекочитаемом формате («июнь 2025»).

### ADR-017: Статус TRANSIT — для бывших плательщиков и старых карточек после переоформления

**Дата:** 2026-05-21
**Статус:** Принято
**Контекст:** При сверке реестра клиентов с CEO24 обнаружены два кейса, которые в существующих статусах (ACTIVE/CHURNED/SUSPENDED/PROSPECT) описать нельзя. (1) Юр.лица, переводящие оплату за **другого** клиента (например, ПРОМСТРОЙХОЛДИНГ платит за Гаджикурбанова, Сбербанк/Реутова — за ТСН Белое озеро). Если поставить им статус CHURNED — они попадут в счётчик оттока, чем не являются: клиент-получатель услуги не уходит. (2) Старые карточки клиентов после переоформления компании на новый ИНН (Бристоль Сервис, Гонцова/Новая Опалиха). В системе оказывается две active-записи с одинаковой АП — двойной счёт. Та же проблема с CHURNED-маркировкой.
**Решение:** Введён новый `OrgStatus.TRANSIT`. Семантика — «больше не платит за себя» (либо никогда не платил за себя, был транзитным плательщиком за другого). Поведенчески зеркально CHURNED по части начислений: `ChargeService.rebuild_for_organization` останавливает начисления с `churn_month` для `status in (CHURNED, TRANSIT)`. PATCH `/organizations` авто-проставляет `churn_month` при переходе в TRANSIT по той же логике (месяц последнего платежа). Но в счётчики оттока TRANSIT **не** включается — в `dashboard.py` TRANSIT исключён из `stopped_since_year_start` и из знаменателя `paying_base` для churn_rate. В `active_clients` тоже не входит (`status == ACTIVE` фильтр уже автоматически отсекает).
**Последствия:** Чистая семантика «не отток, не активный, а исторический плательщик». В Cash Inflow деньги транзитных плательщиков переезжают на реального клиента через скрипт `reassign_transit_payments.py` (см. ADR-018). Миграция `c4f1a2e8b3d6` (`ALTER TYPE orgstatus ADD VALUE 'transit'`) + фикс `d8e2b91f5a7c` (RENAME → 'TRANSIT'): SQLAlchemy сериализует Python `enum.Enum` по `.name` (UPPERCASE), исторические значения в БД хранятся как 'ACTIVE'/'CHURNED' и т.д., а первоначальная миграция ошибочно добавила lowercase — фикс необходим, чтобы PATCH'и не падали по invalid enum value. На фронте «Транзит» добавлен в фильтры статусов ReportsView/DebtorsView/ClientCardView.

### ADR-018: Дедупликация платежей — оставляем версию из 1С-реестра, удаляем парные из банк-выписки

**Дата:** 2026-05-21
**Статус:** Принято
**Контекст:** Софья в комментариях к задаче №886 систематически указывала «у вас оплаты прошли дважды». Замеры подтвердили: на 6 произвольных клиентах коэффициент удвоения **ровно 2.00×**. Один реальный платёж попал в БД дважды: при импорте реестра 1С «Оплата от покупателей» (`payments.xls`, контракт `1C-PAYMENTS`) и при импорте банковской выписки (контракт `BANK-IMPORT`). Парсер не дедуплицировал между источниками. Масштаб: 656 групп `(organization_id, doc_date, amount)` где документы из обоих источников; 656 групп — все pattern `clean_pair` (1+1); фантомных денег ~₽18.3 млн.
**Решение:** **Source of truth — `payments.xls`** (реестр 1С). Причины: (а) содержит полное назначение платежа (счёт, период, договор), на котором AllocationService строит AR-леджер; (б) на банк-копиях в этой паре **0 аллокаций** (леджер исторически собирался только из payments.xls). Удаление банк-копий безопасно: не нужно ни перепривязывать аллокации, ни пересобирать леджер. Дедуплицируем только cross-source clean_pair группы — intra-source дубли (317 групп) **не трогаем**: это реальные множественные платежи на одну сумму в один день (видно по разным номерам счетов в `raw_name`). Применено как одна SQL-транзакция (`/tmp/dedup.sql`): 635 банк-документов удалено, 0 аллокаций затронуто. Бэкап до операции — `/root/backups/ceo24-pre-dedup-2026-05-21-1026.dump`.
**Последствия:** В Document-таблице больше нет cross-source clean_pair дублей (`HAVING count(*) = 2 AND count(DISTINCT import_run_id) = 2` → 0). KPI дашборда не изменились (MRR факт, Сбор, Cash Inflow и так считались только из аллокаций); поправилась карточка клиента → вкладка «Платежи» и любые отчёты с total суммой платежей. Парсер импорта **не правился**: эта операция — однократная чистка исторических данных. Чтобы дубли не появлялись впредь, дальнейший фикс — на этапе импорта: при загрузке банк-выписки проверять, есть ли в `documents` запись с тем же `(organization_id, doc_date, amount)` из `payments.xls`; если есть — bank-документ не создавать. Кандидат на следующую итерацию (в backlog).

### ADR-019: Полный срез файла 1С хранится в основной БД через DebtSnapshot

**Дата:** 2026-05-27
**Статус:** Принято
**Контекст:** При работе с импортом файла «Задолженность покупателей» из 1С обнаружились две проблемы. **(1) Парсер терял данные.** На боевом файле 24.05.2026 (6058 строк) парсер падал на 188 строках: служебные `<…>` 1С-маркеры, Корректировки долга/реализации, разные написания допсоглашений («Доп. согл.», «Доп сог.»), нестандартные номера договоров (`0ББП-...`, `Альфа ...`, `№<номер>`), физлица без ИНН в колонке B, договоры без префикса «Договор» в начале строки. Эти строки + их потомки не попадали в БД. **(2) Авансы и предоплаты не хранились вообще.** Основная модель `Organization` хранит только `total_debt` = `debt_end` покупателя; поля `advance_start/end`, `prepay_in/used` и иерархия с суммами на уровне договора/документа игнорируются. На текущем файле это ~6.9 млн ₽ авансов клиентов, нигде не учтённых. CEO нужно «проверять, что импорт всё разнёс правильно, как в исходном файле».
**Решение:** **(1)** Расширен парсер `debt_report.py`: GROUP_MARKER для `<…>`, DOCUMENT для Корректировок/Списаний/Возвратов, нормализация «Доп* сог*», `_BARE_CONTRACT_RE` с поддержкой кириллицы, `_CONTAINS_DOGOVOR_RE`, `_PERSON_NAME_RE` для ФИО без ИНН. **(2)** Введены две новые таблицы — `debt_snapshots` (1-к-1 с `import_runs`) и `debt_snapshot_rows` (флэт-список строк с иерархией через `parent_row_id`). Сохраняются все 8 числовых колонок исходного файла, `raw_name`, `row_index` (порядок 1С), плюс опциональные FK на `Organization`/`Contract`/`Document` для сверки и навигации.
**Решение хранить в той же БД, а не в отдельной:** (а) JOIN с `Organization.total_debt` для сверки идёт одним запросом без cross-DB JOIN; (б) транзакционная целостность — snapshot пишется в той же транзакции, что и основной импорт (`process_import` + `_build_debt_snapshot`); (в) бэкап один и согласованный (избегаем рассинхрона между двумя СУБД); (г) объём данных — ~6 тыс. строк на импорт, при еженедельном импорте это ~300 тыс. строк/год — для PostgreSQL это копейки. Отдельная БД дала бы изоляцию, но создала бы реальную операционную сложность без выигрыша. **Решение хранить и физлиц без ИНН:** в основной `Organization` положить нельзя (UNIQUE inn), но в snapshot — `organization_id=NULL`, данные не теряются. Backfill для уже существующих ImportRun — отдельный скрипт `backend/scripts/backfill_debt_snapshot.py`, парсит исходный файл и связывает строки с актуальными сущностями БД.
**Последствия:** В UI «1С-вид» в разделе «Должники» (`GET /debt-snapshots/latest`) пользователь видит выбранный импорт ровно как в Excel-файле, с подсветкой расхождений между `DebtSnapshotRow.debt_end` (файл 1С) и `Organization.total_debt` (текущая БД). На боевом файле сверка показала точное математическое совпадение: 4 818 185 ₽ (`/debtors`) + 1 008 750 ₽ (РРСС excluded) + 32 970 ₽ (КАШИН ФЛ без `Organization`) = **5 859 905 ₽** = `snapshot.total_debt_end`. Корректировки долга/реализации теперь распознаются парсером как DOCUMENT (8 клиентов с ранее теряемыми корректировками — ИМПЕРИАЛЪ ТСЖ, СОСНОВЫЙ БОР ТСЖ и др. — больше не висят с фантомным долгом). DocType.CORRECTION в enum пока не добавлен, маппится в `SALE` с `raw_name="Корректировка..."`; кандидат на отдельную итерацию. **Ограничения:** при удалении ImportRun каскадно удаляется snapshot (CASCADE) — это намеренно, snapshot живёт ровно столько же. При удалении Organization/Contract/Document snapshot-строки сохраняются с FK = NULL (SET NULL) — исторический снимок не должен ломаться от текущих операций.

### ADR-020: Проработка дебиторки — отдельная таблица, привязанная к Organization, а не к строке snapshot

**Дата:** 2026-05-27
**Статус:** Принято
**Контекст:** В UI «1С-вид» (см. ADR-019) Софья попросила добавить per-row статус «Проработано / В работе» и текстовый комментарий — менеджер прямо в строке должника отмечает, что разобрано, и оставляет заметку. Возникла развилка: хранить эти поля **(а)** прямо в `DebtSnapshotRow`, или **(б)** в отдельной таблице с привязкой к `organization_id`. Snapshot — immutable срез из 1С, который пересоздаётся при каждом новом импорте (раз в неделю); если хранить статус прямо в строке, на следующем импорте вся проработка обнуляется. Если привязать к `import_run_id`, придётся отдельно решать, как переносить состояние между неделями. Snapshot — это «фото момента», заметки же — история по клиенту, которая должна жить независимо от импортов.
**Решение:** Новая таблица `debtor_workflow` с PK = `organization_id` (1-к-1 с `Organization`), полями `status` (`not_started`/`in_progress`/`done`), `comment`, `updated_at`, `updated_by_id`. CASCADE на удаление организации, SET NULL для `updated_by_id`. API — `PUT /api/v1/debtor-workflow/{org_id}` (upsert; 400 при пустом payload, 404 если организации нет). В ответе `/debt-snapshots/{id}` добавлено `workflow_by_org: {org_id: serialized_workflow}` — одним SELECT через `load_workflow_map(session, org_ids)`, чтобы фронт получал состояние вместе со снимком без N+1. Заодно добавлен query-параметр `only_regular: bool` — отсекает buyer-строки, где Organization не `in_registry` или статус не в `{active, suspended, churned}` (транзитные и потенциальные пропадают вместе с дочерними contract/document по `parent_row_id`). Это закрывает второе требование Софьи — «Только наши клиенты» в реестре дебиторки.
**Последствия:** Менеджер заполняет статус и комментарий прямо в TreeTable 1С-вида (PrimeVue `Select` + `Textarea` с inline-сохранением на blur). При следующем переимпорте 1С заметки сохраняются, потому что привязка по `organization_id`, а не по snapshot row. При удалении Organization (`DELETE FROM organizations`) workflow удаляется каскадно — намеренно. При смене ИНН (новая Organization для того же клиента) проработка не переедет автоматически — редкий кейс, на текущем этапе игнорируем. **Backfill:** не требуется — таблица пустая, новые записи появляются по мере того, как менеджер открывает 1С-вид. **Альтернатива, которую не выбрали:** хранить в `DebtSnapshotRow` с переносом состояния скриптом при импорте. Отказались, потому что (а) копирование состояния между снимками нетривиально (изменилась структура долга, какой-то клиент пропал, появился новый); (б) добавлять CRUD-поля к immutable срезу нарушает его семантику.


### ADR-021: DEBUG-флаг скрывает /docs, /openapi.json, /redoc в production

**Дата:** 2026-05-28
**Статус:** Принято
**Контекст:** До 2026-05-28 эндпоинты `/docs`, `/redoc`, `/openapi.json` были публично доступны на проде (`https://ceo.pass24pro.ru/docs`). Они не показывают данные — только схему API. Однако схема API облегчает разведку атакующим (видны все эндпоинты, payload'ы, валидаторы), что особенно неприятно после инцидента 2026-05-13 (когда какое-то время `/organizations` был открыт без токена). В логах backend регулярные bot-сканы на `.env`, `.git/config`, `phpunit` — фон шумовых атак ненулевой.
**Решение:** Добавил `Settings.DEBUG: bool = False` в `app/core/config.py`. В `app/main.py`:
```python
app = FastAPI(
    title="CEO24", version="0.1.0",
    docs_url="/docs" if settings.DEBUG else None,
    redoc_url="/redoc" if settings.DEBUG else None,
    openapi_url="/openapi.json" if settings.DEBUG else None,
)
```
В production `.env` `DEBUG` не выставлен → схема API закрыта (404). Локально для разработки `DEBUG=true` в `backend/.env` (один раз) + рестарт backend → схема снова доступна. Smoke-test проверяет `/api/v1/docs == 404` (важно: `/docs` без `/api/v1/` ловит SPA-fallback nginx и отдаёт `index.html` со статусом 200 — это норма, не сигнал что docs открыт).
**Последствия:** Поверхность атаки уменьшена без потери удобства разработки. UI-смены не было — никто из пользователей `/docs` не использует. Smoke-скрипт `scripts/post-deploy-smoke.sh` валидирует, что `/api/v1/docs` возвращает 404 после каждого деплоя — если ENV случайно протёк `DEBUG=true` в прод, smoke провалится. Аналогичная защита — для `/api/v1/openapi.json`. В CI этот smoke не запускается (он против прода через HTTPS), используется руками после `docker compose up -d`.

### ADR-022: «К списанию» — действие, «Поставщик» — статус (SUPPLIER)

**Дата:** 2026-05-29
**Статус:** Принято
**Контекст:** Софья прислала запрос на «новые статусы клиента: к списанию и поставщик» (#96538): «сейчас всех отмечаю оттоком». Без уточнения семантики легко было сделать два новых значения OrgStatus и забыть. CEO (Алексей Хромов) прояснил:
- **«К списанию»** означает невозвратный долг. Это не статус, который клиент носит долго, а **действие**: после нажатия — клиент должен перестать участвовать в общей задолженности (`total_debt → 0`), перейти в Отток (CHURNED), с месяцем отключения = сегодня. То есть «списать» = «навсегда убрать из активной дебиторки».
- **«Поставщик»** означает контрагента-возврат: деньги вернулись к нам на расчётный счёт от поставщика (не наша подписочная выручка). Не участвует в АП, не в churn rate, не в любой другой статистике. По сути — `excluded_from_analytics=True` через именованный канал.
**Решение:**
1. **`OrgStatus.SUPPLIER`** — новое значение enum (миграция `f3d7a1c6b9e0`, `ALTER TYPE orgstatus ADD VALUE 'SUPPLIER'`). `dashboard_service.excl()` расширен на `Organization.status != SUPPLIER`. `/billing/debtors` и `/billing/segments` параллельно фильтруют. На фронте — пункт «Поставщик» добавлен в 4 селектора статуса (BillingView / ReportsView / DebtorsView / ClientCardView).
2. **`POST /api/v1/organizations/{inn}/write-off`** — действие списания, атомарно: `total_debt = 0`, `status = CHURNED`, `churn_month = today.replace(day=1)`. Запись в `audit_log` (`action='organization.write_off_debt'`) с actor email и старой суммой долга. UI — кнопка «Списать» в Реестре должников (только при `total_debt > 0`) + `ConfirmDialog` с предупреждением «действие необратимо, но останется в audit log». Для этого подключён `ConfirmationService` в `main.ts` + `<ConfirmDialog/>` в `App.vue`.
**Последствия:** SUPPLIER ведёт себя одинаково с `excluded_from_analytics=True` — но даёт UX-понятный способ пометить контрагента без захода в admin. Списание долга идемпотентно (повторное нажатие просто запишет новый audit-log и обнулит то, что уже 0). Audit-log позволяет провести аудит «что и кому Софья списала за месяц» одним запросом `SELECT FROM audit_log WHERE action='organization.write_off_debt'`. **Альтернатива, которую не выбрали:** добавить статус `WRITE_OFF` (списан) как промежуточный между ACTIVE и CHURNED. Отказались, потому что CEO явно сказал — это действие, не state; держать дополнительный enum-значение только для эфемерного перехода = ненужная сложность.

### ADR-023: Отток без ложных срабатываний — гибрид «леджер + статус»

**Дата:** 2026-06-03
**Статус:** Принято
**Контекст:** Софья прислала экспорт «Цифры оттока с комментариями» (задача #1024, 02.06): из ~32 клиентов в составе метрики «перестали платить с начала года» подавляющее большинство — активные, оплатившие на полгода-год вперёд (Кутузовская Ривьера, Мартемьяново, Рассказовка и т.д.). Реальный отток — единицы. Корень: метрика считалась по «последний платёж > 60 дней назад», что ловит и предоплативших вперёд. CEO (Алексей Хромов) выбрал вариант **гибрид: леджер + статус**.
**Решение:**
1. **Леджер исключает предоплату.** Введён helper `dashboard_service.max_covered_month` — последний месяц начисления, полностью закрытый аллокациями (Σ alloc ≥ amount). `prepaid_current_ids` = клиенты, у кого этот месяц ≥ текущего (оплачено по текущий месяц или вперёд). Такие клиенты НЕ считаются оттоком, даже если последний платёж был давно.
2. **Статус фиксирует ручной отток.** `stopped_since_year_start_ids` = (авто-детект: последний платёж в этом году, > 60 дней назад, НЕ предоплачен, НЕ TRANSIT) ∪ (вручную помеченные `CHURNED` с `churn_month` этого года).
3. Единый источник id для плитки дашборда (`dashboard.py`) и drill-down экспорта (`composition_service._build_stopped`) — инвариант «плитка = состав» сохранён. `churned_60d` тоже исключает предоплативших.
**Последствия:** Метрика отражает реальное прекращение платежей, а не «давно не платил, потому что оплатил вперёд». Различие «перестал платить» (есть непогашенные начисления) vs «ушёл» (ручной CHURNED) теперь явно отражено в подсказке плитки. Прод: 32 → 31. **Не выбрали** чисто ручной режим (только статус CHURNED) — он точнее, но не ловит новые случаи автоматически и требует постоянной ручной разметки.
