# CEO24 — Учёт абонентской платы (AR-леджер): дизайн-спецификация

- **Дата:** 2026-05-18
- **Статус:** утверждён пользователем
- **Автор:** сессия Claude Code
- **Связанные документы:** `agent_docs/backlog.md` (P3.1), `docs/superpowers/plans/2026-05-15-p31-bank-reconciliation.md` (поглощается этой фичей), `docs/superpowers/specs/2026-05-15-ceo24-screens-redesign-design.md`

## 1. Контекст и проблема

При редизайне дашборда (2026-05-16) график собираемости показал март 2026 на уровне 127%
(факт 5.72M против плана 4.48M). Backlog предполагал «задвоенный импорт либо непериодические
поступления». Расследование на копии production-БД (бэкап 2026-05-16) показало другое.

**Корневая причина — дефект определения метрики, а не ошибка данных:**

- `collection-trend` и `_fact_mrr_for_month` считают «факт сбора за месяц» как сумму всех
  `PAYMENT`-документов, чья **дата прихода на счёт** попала в календарный месяц.
- Сравнивают это с планом = подписочный MRR (Σ `Organization.monthly_ap`) — обязательство
  за один месяц.
- Банк-выписка — валовой приток денег: туда вперемешку падают текущая абонплата, авансы и
  погашение старых долгов.

Разбивка поступлений марта 2026 по периоду, за который реально платят: из 5.72M доказуемо
не за март минимум 3.28M (авансы за апрель 1.39M, погашение февраля 0.42M, старые долги
2019–2025 ≈1.3M). Реальная собираемость марта — 25–55%, не 127%. Дефект системный: «нормальные»
93–98% января/февраля/апреля — совпадение, метрика меряет не то во всех месяцах.

Задвоенный импорт **опровергнут**: `PAYMENT`-документы из отчёта о задолженности имеют
`amount = 0` (2100 шт.), все суммы приходят только из одной банк-выписки (711 платежей).

**Побочные дефекты данных, выявленные при расследовании:**

- Парсер периодов (`extract_payment_info`) ненадёжен: `_PERIOD_SLASH_RE` ловит любые `ДД/ГГГГ`,
  включая даты в номерах договоров; нет валидации месяца 1–12 (отсюда мусор `month=63`,
  `year=1031`). ~1.2–1.3M/мес платежей с `period = NULL`.
- Один настоящий дубль (МАРВЭКС-М, `doc_number 148` дважды) — ключ дедупа должен был поймать.

## 2. Цель и не-цели

**Цель:** заменить дефектную метрику полноценным учётом абонентской платы по принципу
дебиторского леджера — лента месячных начислений на каждого клиента и разнесение входящих
платежей по этим начислениям. Это даёт честную собираемость, структуру поступлений и видимость
картины платежей (клиенты платят неравномерно: за прошлые месяцы, текущий, авансом на полгода-год).

**Не-цели:**

- Интеграция с 1С по API (1С остаётся master, данные приходят файлами-выгрузками).
- Воронка продаж (P3.6).
- Ролевая модель manager/viewer (P3.3) — редактирование пока доступно любому авторизованному.

Фича поглощает backlog-пункт P3.1 «Сверка платежей с банком»; план
`2026-05-15-p31-bank-reconciliation.md` считается замещённым.

## 3. Доменная модель

- 1-го числа каждого месяца клиенту начисляется обязательство = абонплата (АП) за начавшийся
  месяц. В 1С это материализуется как документ «Реализация».
- Платежи приходят неравномерно: один платёж может покрывать несколько месяцев, в том числе
  прошлых (погашение долга) и будущих (аванс).
- «Факт сбора за месяц» — не сумма платежей, а результат **аллокации**: каждый платёж
  раскладывается по одному или нескольким месячным начислениям.
- Тариф клиента может меняться во времени — начисление месяца использует тариф, действовавший
  в этом месяце.

## 4. Модель данных

Три новые таблицы + Alembic-миграция. Существующие модели не ломаются.

### 4.1 `tariff_period` — история тарифа клиента

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID PK | |
| `organization_id` | FK organizations | клиент |
| `valid_from` | date | месяц, с которого действует тариф |
| `monthly_amount` | Decimal(12,2) | сумма АП/мес |
| `created_by` | FK users, nullable | кто внёс (аудит) |
| `created_at` | datetime | |

`Organization.monthly_ap` остаётся денормализованным «текущим тарифом» (его читает текущий код);
обновляется при добавлении нового `tariff_period`.

### 4.2 `monthly_charge` — начисление за месяц

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID PK | |
| `organization_id` | FK organizations | клиент |
| `year`, `month` | int | период начисления |
| `amount` | Decimal(12,2) | сумма начисления |
| `source` | enum `realization_1c` / `synthetic_tariff` | происхождение |
| `source_document_id` | FK documents, nullable | ссылка на `SALE`-документ, если из 1С |
| `created_at` | datetime | |

Уникальность: `(organization_id, year, month)`.

### 4.3 `payment_allocation` — разнесение платежа на начисления

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID PK | |
| `payment_document_id` | FK documents | банковский платёж |
| `monthly_charge_id` | FK monthly_charge, nullable | начисление; NULL = нераспознанный остаток |
| `allocated_amount` | Decimal(12,2) | сколько этого платежа ушло на это начисление |
| `basis` | enum `explicit_period` / `fifo` / `advance` / `manual` | основание разнесения |
| `is_manual` | bool | правил ли человек |
| `created_at`, `updated_at` | datetime | |

Один платёж → несколько строк аллокации (оплата за полгода = до 6 строк).

### 4.4 Источник начислений

- **Закрытые месяцы:** начисление = subscription-`SALE`-документы (реальная Реализация из 1С,
  фильтр `contract_type = SUBSCRIPTION`). `source = realization_1c`, `source_document_id`
  ссылается на документ. Период = месяц `doc_date`.
- **Текущий и будущие месяцы:** начисление = `monthly_ap` из `tariff_period` (Реализации ещё
  нет, но авансы уже приходят). `source = synthetic_tariff`.
- Начисления генерируются с месяца первой Реализации клиента до текущего месяца включительно.
  Синтетические будущие начисления создаются движком аллокации по необходимости (когда платёж
  уходит авансом), горизонт +24 месяца — см. §6.

## 5. Парсер периодов

Новый модуль `backend/app/parser/period_extraction.py` (выносится из `bank_statement.py`).

**Выход на один платёж (из текста назначения):**

- `periods: list[(year, month)]` — явно названные месяцы (0, 1 или диапазон).
- `coverage_months: int | None` — если текст указывает «на N месяцев / полгода / год» без
  названных месяцев.
- `payment_kind: subscription | other` — по ключевым словам («доступ», «PASS24» против
  «оборудование», «монтаж», «поставка»).
- `invoice_number`, `contract_number`, `tariff` — как сейчас.

**Поддерживаемые шаблоны периода:**

| Шаблон | Пример | Результат |
|---|---|---|
| Один месяц | «за март 2026», «03/2026» | `[(2026,3)]` |
| Месяц без года | «за март» | год выводится по дате платежа |
| Диапазон | «январь-июнь 2026», «с 01.2026 по 06.2026» | `[(2026,1)…(2026,6)]` |
| Количество | «за 3 месяца», «на полгода», «на год» | `coverage_months = 3/6/12` |
| Нет периода | «доступ на месяц», «по счёту № 148» | `[]` |

**Фикс ложных срабатываний:**

- Месяц валидируется `1..12`, год — `2019..текущий+1`; вне диапазона — отбрасывается.
- Slash-формат: год форсируется `20\d{2}`, добавляются negative lookbehind/lookahead
  `(?<![\d/\-])…(?![\d/])` — не цеплять даты внутри номеров договоров.
- Вывод года для месяца без года: год, при котором период ближе всего к дате платежа (±6 мес).

`Document.period_year/period_month` остаются (заполняются первым периодом для совместимости),
но источник истины по разнесению — `payment_allocation`.

## 6. Движок аллокации

Два сервисных модуля (по образцу плоского `import_service.py`):

- `backend/app/services/charge_service.py` — строит ленту `monthly_charge` клиента.
- `backend/app/services/allocation_service.py` — разносит платежи по начислениям.

**Принцип:** аллокация детерминирована и пересчитываема — результат есть чистая функция от
(начисления, платежи, ручные правки). При любом изменении клиент пересчитывается с нуля.

**Лестница приоритетов для одного платежа** (платежи клиента обрабатываются в хронологическом
порядке `doc_date, doc_number, id`):

1. **Явные периоды** (`periods`) → заполняются именно эти начисления, от старого к новому, каждое
   до его остатка. Нет начисления на будущий месяц — создаётся синтетическое из тарифа.
2. **`coverage_months = N`** без названных месяцев → N самых старых незакрытых начислений.
3. **Нет периода** → FIFO: гасится самое старое начисление с остатком.
4. **Остаток платежа** после п.1-3 → перелив: дальше по FIFO, затем авансом в синтетические
   будущие начисления (горизонт 24 месяца); финальный остаток → строка с `monthly_charge_id = NULL`
   (бакет «не определён»).

**Классификация:** только `payment_kind = subscription` платежи входят в аллокацию против
начислений. `other` (оборудование, проекты) в леджер не попадают — учитываются отдельным
сегментом «структуры поступлений». Платежи с `amount = 0` (debt-report заглушки) фильтруются.

**Пересчёт и ручные правки:** `recompute_for_organization(org_id)` удаляет авто-аллокации
(`basis ≠ manual`), сохраняет ручные (`is_manual = true`), вычитает их из остатков и
переразносит остальное. Ручная правка из UI не перезатирается.

**Когда запускается:** после bank-импорта — для затронутых клиентов; после правки тарифа или
ручной аллокации — для одного клиента; `recompute_all()` — для разового backfill.

## 7. Backfill существующих данных

Скрипт `backend/scripts/build_ledger.py` — идемпотентный, перезапускаемый. Реимпорт выписки
не нужен: текст назначения уже в `Document.raw_name`.

1. Alembic-миграция создаёт 3 таблицы.
2. Seed `tariff_period`: по строке на клиента с `monthly_ap > 0`; `monthly_amount` = текущий
   `monthly_ap`; `valid_from` = первая известная активность (ранний из первого subscription-`SALE`,
   первого платежа, `contract_date`).
3. Построить `monthly_charge` через `charge_service` для всех клиентов.
4. Переизвлечь периоды: новый `period_extraction` по `raw_name` каждого банк-платежа, обновить
   `Document.period_year/period_month`.
5. `recompute_all()` — разнести все subscription-платежи.

**Безопасность:** прогон сначала на локальной диагностической копии (сверка
`Σ аллокаций == Σ subscription-платежей`, март не 127%, регрессионный тест). На production —
после деплоя кода, с ручным дампом перед запуском.

## 8. API и метрики

«Собираемость» и «структура поступлений» — два среза одних `payment_allocation`: первый группирует
по месяцу начисления, второй — по месяцу прихода платежа. Сумм по `doc_date` больше нет.

**Дашборд:**

| Эндпоинт | Что | Логика |
|---|---|---|
| `GET /dashboard/collection-trend` (переработка) | Собираемость периода | месяц M: `accrued` = Σ `monthly_charge` за M; `collected` = Σ аллокаций на начисления M; `ratio`; флаг `is_current_month` |
| `GET /dashboard/cash-inflow` (новый) | Структура поступлений | месяц прихода M: стек `current` / `advance` / `arrears` / `undetermined` / `non_subscription` |
| `GET /dashboard/summary` (правка) | KPI | `current_month_collected`, `collection_rate_fact` — из леджера |
| `GET /dashboard/aging`, `/aging/{bucket}` (переработка) | Просрочка | бакеты по сумме непокрытых `monthly_charge`, возраст — по месяцу начисления |
| `GET /dashboard/mrr-plan-vs-fact` (переработка) | План/факт | факт = собираемость периода из леджера |
| `GET /dashboard/payment-matrix` (переработка) | Шахматка | ячейка = Σ аллокаций клиента на начисление месяца |

Текущий месяц помечается `is_current_month` — фронтенд рисует приглушённо (начисление полное,
месяц не закрыт).

**Карточка клиента:**

| Эндпоинт | Что |
|---|---|
| `GET /organizations/{inn}/ledger` | лента начислений: за месяц — `accrued` / `allocated` / `outstanding` / статус (оплачено/частично/долг/аванс) + платежи с разнесением |
| `PUT /payments/{document_id}/allocations` | ручная правка: тело — список `{year, month, amount}`; строки помечаются `is_manual`, запускается пересчёт клиента |
| `GET /organizations/{inn}/tariffs` + `POST` | история тарифа; добавление `tariff_period` пересобирает начисления и пересчитывает клиента |

Все эндпоинты — под существующим router-level `Depends(get_current_user)`. Ролевого
разграничения правок пока нет (консистентно с редактируемой карточкой из редизайна).

## 10. Тестирование

**Backend** (SQLite in-memory + синтетические фикстуры, файлы не нужны):

- `period_extraction` — юнит-тесты на реальных строках назначений: ложные срабатывания (даты в
  номерах договоров, мусор `month=63`), диапазоны, «на N месяцев», вывод года.
- `charge_service` — сборка начислений из `SALE` + синтетика пропусков.
- `allocation_service` — лестница приоритетов: явный период, `coverage_months`, FIFO, перелив,
  горизонт аванса, сохранение ручных аллокаций, исключение `non_subscription`, детерминированность.
- API-тесты новых/изменённых эндпоинтов.
- Регрессионный тест: собираемость марта 2026 вменяемая (не 127%).

**Frontend:** `vue-tsc` чисто + успешный build (юнит-тестов фронта в проекте нет).

## 11. Выкатка

Деплой редизайна рабочих экранов (коммит `3d94c1a`, ещё не на production) и этой фичи
**бандлятся в один деплой** — выкатывать дашборд с битым графиком отдельно смысла нет.

Порядок: Alembic-миграция → деплой кода (`docker compose build && up -d`) → `build_ledger.py`
на production. Ручной дамп БД перед миграцией. Деплой требует подтверждения пользователя
(shared-система, 5 пользователей).

## 12. Зафиксированные решения

- Обе метрики на дашборде: собираемость периода (%) и структура поступлений (стек).
- Период=NULL после улучшения парсера обрабатывается аллокацией (FIFO), не остаётся «дырой».
- Подход — полный AR-леджер с персистентными таблицами (`monthly_charge`, `payment_allocation`,
  `tariff_period`), а не расчёт на лету.
- Источник начислений — реальная Реализация из 1С для закрытых месяцев, синтетика из тарифа
  для текущего/будущих.
- Перелив при явном периоде: излишек уходит дальше по FIFO/авансу.
- Горизонт аванса — 24 месяца.
- Соседние метрики (aging, шахматка, mrr-plan-vs-fact) переводятся на леджер в этой же фиче.

## 13. Вне скоупа

- Сверка платежей с документами-счетами по `invoice_number` (более точная привязка периода) —
  возможное развитие, не входит.
- Удаление debt-report `PAYMENT`-заглушек с `amount = 0` — отдельная задача чистки.
- Дубль МАРВЭКС-М (`doc_number 148`) — узкий баг дедупа, фиксится отдельно.
- Уведомления/алерты по новым метрикам (P3.4).
