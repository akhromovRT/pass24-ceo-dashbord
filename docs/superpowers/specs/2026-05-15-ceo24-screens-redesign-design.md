- **Статус:** утверждён пользователем

## 1. Проблема

Три рабочих экрана дашборда не выполняют свою функцию — «быть полезными взгляду для принятия управленческих решений»:

1. **Dashboard** — график «MRR план vs факт (12 мес)» показывает 7 пустых месяцев (платежи импортированы только с 01/2026). KPI «-23.2% м/м» сравнивает апрель с мартовской аномалией (127% — вероятно задвоенный импорт) и пугает зря. «Открытые алерты: 287» — голый счётчик без действий.
2. **Реестр клиентов** — плоская таблица, у большинства строк ключевые колонки (АП/мес, Долг, Оценка) пустые («—»). Нет сегментации, итогов, акцентов. Карточка клиента — только просмотр, ничего нельзя править.
3. **Должники** — заглушка (`DebtorsView` — placeholder).

## 2. Цели и не-цели

**Цели:**
- Dashboard — экран решений в один viewport: честные графики (только месяцы с данными), KPI вокруг вопроса «собираем ли мы деньги», панель «Требуют внимания» вместо счётчика алертов.
- Реестр клиентов — аналитическая шапка с сегментами + шахматка платежей как режим.
- Карточка клиента — полноценный рабочий инструмент: все поля редактируемые, статус меняется, видна история взаимодействия (платежи/документы).
- Должники — отдельный реестр с фокусом на задолженности; статус клиента меняется прямо из списка.

**Не-цели:**
- P3.1 «Сверка платежей с банком» — отдельная спецификация и план.
- Роли manager/viewer (P3.3) — не трогаем; всё под admin.
- Новые таблицы БД — все нужные поля уже есть в моделях. Миграции не требуются.
- Audit log правок — отдельный пункт backlog, вне scope.
- Разбор аномалии марта 127% — фиксируется как задача проверки данных в плане, не блокирует UI.

## 4. Бэкенд

### 4.1. `GET /dashboard/summary` — расширение

Добавить в ответ (существующие поля сохраняются для обратной совместимости):
- `current_month_label` — `YYYY-MM` текущего (незакрытого) месяца
- `current_month_collected` — сумма PAYMENT за текущий месяц
- `days_passed`, `days_in_month` — для индикатора прогресса месяца
- `debt_90plus_amount`, `debt_90plus_share` — сумма и доля корзины 90+ от общего долга
- `collection_rate_fact` — `mrr_fact / mrr_plan` (доля, 0–1+)

`mom_mrr_delta_pct` остаётся в payload, но на фронте уходит из заголовка KPI (показывается как вторичная подпись, без алармизма).

### 4.2. `GET /dashboard/collection-trend` — новый

Заменяет на фронте `mrr-plan-vs-fact`. Возвращает **только месяцы, где есть хотя бы один PAYMENT** (отсекает пустую историю). Каждый элемент: `{year, month, label, plan, fact, ratio}`. Если месяцев с данными нет — пустой массив (фронт показывает empty-state).

### 4.3. `GET /dashboard/attention` — новый

Агрегирует `Alert` со `status=OPEN` по `alert_type`. Возвращает массив, отсортированный по `severity` затем по сумме `metric_value`:
```
[{ "type": "large_debt", "label": "Просрочка 90+",
   "count": 57, "amount": 4526339.36, "severity": "critical",
   "route": "/debtors?bucket=90%2B" }, ...]
```
`label` и `route` — статический маппинг по `AlertType`. Фронт показывает топ-5 категорий.

### 4.4. `GET /billing/segments` — новый

Считает по организациям `in_registry=true AND excluded_from_analytics=false`:
- `total` — всего, `mrr_plan` — сумма `monthly_ap`
- `paying` — собираемость закрытого месяца ≥ 95%
- `partial` — 1% ≤ собираемость < 95%
- `not_paying` — собираемость < 1%
- `debtors` — `total_debt > 0`

Собираемость считается так же, как в `payment-matrix` (PAYMENT за закрытый месяц / `monthly_ap`).

### 4.5. `GET /billing/debtors` — обогащение

Существующий эндпоинт дополнить вычисляемыми полями на каждую строку: `months_overdue` (= `total_debt / monthly_ap`), `aging_bucket` (`0-30|31-60|61-90|90+` — та же логика, что в `dashboard/aging`). Поддержать query-параметры `bucket` и `status` для фильтрации (опционально; фронт может фильтровать и сам — ~97 строк).

### 4.6. `PATCH /organizations/{inn}` — новый

Принимает частичный набор полей. **Редактируемые:** `name_display, org_type, status, manager_id, client_since, objects, object_type, cloud_url, system_number, equipment, address, city_region, has_folder, monthly_ap, notes, doc_exchange, in_registry, excluded_from_analytics, excluded_reason`.

**Только для чтения** (источник истины — импорт из 1С/банка): `inn, name_1c, total_debt, payment_score, created_at, contract_1c_raw, active_doc_raw`.

Поведение: Pydantic-схема `OrganizationUpdate` со всеми полями `Optional`; применяются только присланные ключи (`exclude_unset`); обновляется `updated_at`; ответ — обновлённая организация. 404 если ИНН не найден. Валидация: `monthly_ap ≥ 0`, `status` ∈ `OrgStatus`, `org_type` ∈ `OrgType`.

### 4.7. `GET /organizations/{inn}/documents` — новый

Возвращает все `Document` организации, отсортированные `doc_date DESC`. Поля: `doc_type, doc_number, doc_date, amount, period_year, period_month, raw_name`. Это «история взаимодействия» для карточки.

### 4.8. `GET /users/options` — новый

Минимальный список активных пользователей `[{id, name}]` для дропдауна выбора менеджера. Доступен любому аутентифицированному пользователю (в отличие от admin-only `GET /users`).

## 5. Фронтенд

### 5.1. Dashboard (`DashboardView.vue`)

Один viewport, три зоны.

**KPI-ряд (5 тайлов, общий компонент `KpiTile`):**
| Тайл | Значение | Подпись |
|---|---|---|
| MRR факт | факт за закрытый месяц | собираемость N% от плана |
| MRR план | `monthly_ap` сумма | база |
| Сбор: <текущий месяц> | собрано за текущий месяц | N% плана · день X/Y |
| Долг | общий долг | 90+: сумма (доля%) |
| Клиенты | активных | +N за 30 дней |

**Графики (2 в ряд):**
- «Сбор платежей — <год>» — bar (факт) + line (план) по `collection-trend`, только реальные месяцы. Цвет столбца по ratio (≥95 зелёный / ≥70 жёлтый / <70 красный). Empty-state, если данных нет.
- «Структура долга» — горизонтальные бары `aging`, отсортированы 90+ сверху, акцент на 90+. Клик → `/debtors?bucket=<bucket>`.

**Панель «Требуют внимания» (`AttentionPanel`):** топ-5 категорий из `dashboard/attention`, каждая строка — иконка severity, label, count, сумма, кнопка-переход по `route`.

Шахматка платежей **убирается** с дашборда (переезжает в Реестр).

### 5.2. Реестр клиентов (`BillingView.vue`)

Сверху — `SegmentBand`: числа из `billing/segments` + кнопки-сегменты `[Все][Платят][Частично][Не платят][Должники]`. Клик по сегменту фильтрует активную таблицу.

Режимы (`SelectButton`): `[Таблица] [Шахматка] [По договорам] [По реестру]`. «Шахматка» — heatmap из `dashboard/payment-matrix` (перенесён из дашборда). Остальные режимы — как сейчас.

### 5.3. Карточка клиента (`ClientCardView.vue`)

Полноценный редактируемый инструмент.

**Шапка:** название, ИНН, дропдаун статуса (`OrgStatus`) — меняется сразу, отдельной кнопкой (частая операция); инлайн — ключевые метрики (MRR план, долг, payment score).

**Режим редактирования:** кнопка «Редактировать» переводит секции с полями в режим инпутов; sticky-бар внизу «Сохранить / Отмена». Сохранение — `PATCH /organizations/{inn}` только изменённых полей. Read-only поля визуально помечены (серый фон, без инпута).

**Секции полей:**
- *Реквизиты* — `name_display`, `org_type`, `inn` (RO), `status`, менеджер (`manager_id` через `/users/options`), `client_since`
- *Объект и система* — `objects`, `object_type`, `system_number`, `equipment`, `address`, `city_region`, `cloud_url`, `has_folder`, `doc_exchange`
- *Финансы* — `monthly_ap` (editable), `total_debt` (RO), `payment_score` (RO)
- *Заметки* — `notes` (textarea)
- *Аналитика* — `in_registry`, `excluded_from_analytics`, `excluded_reason`

**Вкладки (история взаимодействия):**
- *История платежей* — `GET /{inn}/documents`, таблица по убыванию даты, тип документа цветным тегом
- *Помесячно* — график snapshots (как сейчас)
- *Договоры*, *Объекты* — как сейчас

### 5.4. Должники (`DebtorsView.vue`)

«Реестр должников» — структура реестра с фокусом на долге.

**Шапка `SegmentBand`:** общий долг, число должников, 90+ (кол-во/сумма), средняя просрочка в месяцах. Кнопки-фильтры по корзине aging `[Все][0-30][31-60][61-90][90+]`. Поддержка query-параметра `?bucket=` (переход с дашборда).

**Таблица:** клиент, ИНН, АП/мес, долг, месяцев просрочки, корзина (тег), статус (**редактируемый инлайн-дропдаун** — «менять статусы прямо из списка»), payment score, менеджер. Сортировка по долгу убыв. по умолчанию. Клик по строке (вне дропдауна) → карточка клиента. Изменение статуса — `PATCH /organizations/{inn}`.

## 6. Обработка ошибок

- `PATCH` с невалидным полем → 422 (Pydantic), фронт показывает toast с сообщением.
- Эндпоинты с пустыми данными (`collection-trend`, `segments`) → корректный пустой ответ, фронт рисует empty-state, а не падает.
- Сетевые ошибки в карточке при сохранении → toast «Не удалось сохранить», режим редактирования сохраняется (данные не теряются).
- Несуществующий ИНН в карточке/PATCH → 404 → фронт показывает «Клиент не найден».
